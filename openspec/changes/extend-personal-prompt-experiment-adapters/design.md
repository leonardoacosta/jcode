# Design

## Context

See [proposal.md](proposal.md). The evaluator in `scripts/prepare_personal_prompt_eval.py` freezes candidate banks and trials, but generates only two baseline tiers. Its custom tool set is fixed to `bash,write,todo`; its callback accepts only `bash` and `write`. `Request::Compact` is present in the client wire protocol, but `jcode-harness-api::RuntimeCommand` and its event contract do not expose a compact request/completion pair. These are concrete adapter gaps; this change will preserve routing and continuity as unsupported and record these exact reasons rather than claim simulated behavior.

V7's `report.json` records all 144 actor and assessor slots valid, three supported families baseline-sufficient, zero leads, and routing/continuity unsupported. V8 bound V1–V7 roots before inference and completed valid new isolation/scope screens, but planning assessment stopped at an unattempted slot after Git cache metadata drift. Across V1–V8, 475 actor slots were attempted (470 valid, 5 invalid), 384 assessor slots were attempted and valid, and zero leads were confirmed. V9 registered fresh planning fixtures but stopped at actor slot 022 after a 180-second API watchdog timeout: 21 valid actor results, one interrupted/invalid slot, 14 unattempted actor slots, and 21 valid Luna assessor results. It has no planning screen disposition. V10 was registered and preflighted 24 actor slots across only two independent fixture contexts, omitting mapping. The mismatch with the three-context plateau rule was found before inference, so it contributes 24 unattempted actor slots and no result evidence. V11 preflighted all 36 contexts but its registered criterion incorrectly named V10 (which had no inference) as the fresh planning screen; this lineage mismatch was recorded before inference. V12 binds V1–V11 roots and cumulative counters, uses fresh planning fixtures, and excludes V9's partial results and V10/V11 preflight-only registrations from plateau evidence. V8's two verified, new family screens remain eligible evidence; V1–V7 baseline labels and screen counts are not.

## Goals / Non-Goals

**Goals:** Complete the fresh planning screen over three independently authored contexts; retain original thresholds and candidate/confirmation rules; make a local, bounded plateau claim only when V8's independently authored isolation and scope screens plus V12's planning screen are all complete, valid, and below their existing signal thresholds; bind all predecessor evidence and cumulative counters before inference.

**Non-Goals:** Do not alter the Jcode product API to manufacture adapter support; do not claim a global prompt plateau, candidate benefit, adoption, publication, or production superiority; do not reopen or replace any spent prior slot.

## Decisions

1. **Record exact adapter blockers and exclude those families before inference.** `prepare_child` freezes `bash,write,todo`, `run_pilot` rejects any other custom callback, and callbacks run without network access. The API compact request exists in `crates/jcode-protocol/src/wire.rs`, but the selected harness surface (`crates/jcode-harness-api/src/runtime_commands.rs`, `requests.rs`, and `events.rs`) does not forward it or expose its completion. A product API change is outside this evaluator-only successor; unsupported dispositions remain terminal and explicit.
2. **Use three fresh, independently authored contexts per supported family.** Add distinct planning, isolation, and scope fixtures, each with challenge and useful-action counterexample cases. Freeze their files, references, oracles and prompts before running. Keep the original 3-repetition, paired-control schedule. Only a replicated signal under the existing threshold can open the existing candidate bank; preserve the original practical-effect, boundary, counterexample, and confirmation thresholds.
3. **Define a local evidence plateau prospectively.** Require one complete valid paired actor/assessor screen for planning, isolation, and scope, each covering three independently authored contexts and three repetitions. V8's verified isolation/scope assessments count; the registered successor must supply a fresh planning assessment. If no family meets its registered signal threshold, report `evidence-plateau-within-registered-screen`. Invalid or unknown evidence cannot count. This fixture result is not global and does not prove prompt ineffectiveness.
4. **Bind lineage and counters into registration.** Before inference, hash the complete V1–V11 root inventories and bind each root's registration, report, and audit. Recompute historical attempted/valid/invalid slots, dispositions, candidate decisions, and leads. Keep all history intact; only the two V8 screens with bound fixture, preflight, trial, and assessment receipts advance the prospective screen count. Prior baseline-sufficiency labels do not.
5. **Keep controls and runtime isolated.** Reuse the existing pinned Luna/medium runner, per-slot private session and networkless callback. Snapshot default/current-personal controls and the selected disposable target; refuse drift. Each candidate continues to start from the original personal bytes. Any candidate/confirmation child receives its own fresh no-inference preflight.

## Risks / Trade-offs

- [New fixtures may fail to expose a signal] → Report a plateau only within the exact registered suite; retain task/context denominators and limitations.
- [Historical report schemas differ] → Recompute counters from verified roots using schema-aware parsing; fail registration if a root or required count is ambiguous.
- [Repeated provider failures consume slots] → Preserve the existing stop rule, invalid counts and spent-slot markers; do not replace or reset.
- [Unsupported adapters could be mistaken for negative results] → Report unsupported separately and exclude those families from the plateau claim.

## Migration Plan

Keep V1–V10 unchanged. Extend the existing runner compatibly, add offline tests and fresh independent review, then register V12 with predecessor hashes/counters and V8 screen evidence frozen; bind V9 as an interrupted campaign and V10 and V11 as no-inference preflight dispositions. Run its fresh no-inference preflight before inference. Complete only the supported planning schedule and any threshold-authorized candidate/confirmation stages; assess retained evidence, verify controls/lineage, update tasks, and commit scoped changes. Archive this change only after required gates, review, evidence persistence and history checks pass. No prompt adoption or shared-daemon action is part of this plan.
