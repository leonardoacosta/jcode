## 1. Schema-validated orchestration output → reuse structured SDK for reviews
- Sandcastle source: https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts , symbols `PlanSchema`, `planJson`, `PlanSchema.parse(JSON.parse(planJson))`. Planner output must contain `<plan>` JSON and satisfy a Zod object schema before issue fan-out.
- Jcode differs: already stronger reusable parsing via `HarnessClient.runStructured`, `compileStructuredSchema`, `validateStructuredText`, bounded `maxRetries`, and `StructuredOutputError` (`sdk/typescript/src/client.ts:1433-1468`). No need to import Zod or recreate a planner parser.
- Bounded adoption: under existing `add-structured-headless-review`, reuse current structured parsing for verdict shape, then independently validate revision/check provenance. Malformed/missing output → `inconclusive`, never inferred PASS.
- Acceptance: actual headless CLI + TS client cover missing JSON, wrong enum, extra prose, wrong revision, exhausted retry, cancel and budget outcomes; exactly one verdict object, no prose parsing; stale check evidence cannot authorize pass.
- Counterexample: valid JSON can still lie about tests. Shape validation is not execution evidence or permission.
- Confidence: high source/fit, runtime unverified. Net-new value is reuse/acceptance detail, not a new feature.

## 2. Run cancellation separate from handle disposal
- Sandcastle documented API: https://github.com/mattpocock/sandcastle#sandboxrunoptions , `SandboxRunOptions.signal: AbortSignal`, explicitly cancels one run while leaving its handle usable. **Oct28 cached documentation claim**.
- Jcode differs: `HarnessClient.cancel(sessionId)` sends a server cancellation (`sdk/typescript/src/client.ts:689`); `events()` subscription cleanup removes listeners (`:1063-1096`); `globalEvents` abort closes child subscriptions (`:1120-1132`). Stopping observation and cancelling execution are distinct operations, not interchangeable.
- Bounded adoption: strengthen existing harness contract tests around a cancelled turn followed by another turn on the same client/session. Specify whether abort affects observation or execution before adding a convenience `signal` to `run`.
- Acceptance: cancel during deltas → one terminal event after admitted deltas; no cross-session cancellation; next turn succeeds using the same connection; pre-aborted and repeated cancel do not leak listeners or duplicate terminal events; disconnect remains distinct from cancel.
- Overlap: `add-harness-sdk-contract-tests/proposal.md:14-16` already owns cancel terminal ordering. Reuse it, do not open an AbortSignal feature merely for API symmetry.
- Confidence: medium, Sandcastle implementation not inspected. Jcode boundary distinction confirmed by source.

## 3. Observer failure isolation, not authority-hook suppression
- Sandcastle documented API: https://github.com/mattpocock/sandcastle#all-options , `logging.onAgentStreamEvent`, typed `text | toolCall | raw` events with `iteration` and `timestamp`; callback errors are documented as swallowed so a broken log forwarder cannot kill a run. **Oct28 cached documentation claim**.
- Jcode differs: `HarnessClient.run` invokes `options.onEvent?.(event)` directly before accumulating text or processing terminal events (`sdk/typescript/src/client.ts:1373-1375`); callback throws therefore reject the convenience call. The server turn need not have stopped.
- Bounded adoption: document and test the observer-exception policy first. If isolated telemetry is desired, scope catch/report behavior to an explicitly observational callback, not permissions, tools, or lifecycle hooks. Do not silently redefine all `onEvent` callbacks as ignorable.
- Acceptance: observer throws on first delta and on terminal event; server completion remains observable through a separate subscriber; iterator listeners clean up; chosen client outcome is deterministic; denied permission remains denied even when a diagnostic subscriber fails.
- Overlap: harness contract tests own client event behavior; `add-lifecycle-hooks` owns executable hooks. Keep observational forwarding separate from executable or admission hooks.
- Confidence: medium-high difference from source, adoption conditional on callback contract decision. Sandcastle runtime guarantee unverified.

## 4. Lexically scoped resource cleanup plus settled per-run results
- Sandcastle source: https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts , `MAX_PARALLEL`, `acquire`, `release`, `Promise.allSettled`, `await using sandbox = await sandcastle.createSandbox(...)`, `finally { release(); }`. One rejected worker does not prevent collecting other worker results; lexical disposal and semaphore release have separate scopes.
- Jcode differs: socket/event lifetimes already have explicit cleanup (`sdk/typescript/src/client.ts:1084-1096`), and `run()` returns on `turn_done` or throws on `error` (`:1423-1429`). Preserve these existing abstractions rather than adopting Docker or creating another orchestration layer.
- Bounded adoption: add client contract cases for setup/send failure after subscription and callback/transport failure while consuming events. Ensure every acquired subscription or child connection is released even before normal iteration begins.
- Acceptance: rejected `sendMessage`, disconnect before first frame, thrown callback, iterator early return, and failed cancellation all release owned listeners/children; repeated runs do not accumulate them; one failed parallel client does not terminate an unrelated client.
- Important no-adopt: Sandcastle `.sandcastle/run.ts` calls Reviewer but ignores its result, then identifies completed branches via fulfilled implementation + `commits.length > 0`. Do **not** copy this completion/merge gate. Jcode P08 requires revision/check-bound verdicts, not commits or successful promise resolution (`docs/plans/PRODUCT_ROADMAP.md:223-224`).
- Confidence: high for inspected pattern, medium for specific Jcode failure gaps until exercised.

## Browser/voice fit and blockers
- No inspected Sandcastle source demonstrates browser tab/goal binding, typed help hand-back, microphone capture consent, or transcription authority boundaries. Generic sandbox isolation cannot establish those guarantees.
- No browser/voice adoption candidate justified. Keep existing `add-browser-voice-boundary-acceptance/proposal.md:14-21` as owner, with wrong-tab refusal, typed help return, unavailable bridge, Esc discard, missing mic/key, and transcription-only input acceptance.
- Blockers: Sandcastle README behaviors need implementation/runtime verification before promotion; no verified immutable source commit; callback exception policy needs a deliberate API compatibility decision.
- Recommendation: fold mechanisms 1–2 and cleanup cases into existing P08 work; mechanism 3 is a narrowly bounded policy decision; reject the commit-only review gate. No new OpenSpec proposal needed from this pass.
