## 1. Canonical skill ownership, projected into harness-specific locations
- **Source:** pinned commit above moves skill definitions into `.agents/skills/`; its `.claude/skills` file contains `../.agents/skills` (source diff line 1). Exact source paths: `.agents/skills/grill-with-docs/SKILL.md`, `.agents/skills/pre-release/SKILL.md`, `.claude/skills`.
- **Mechanism:** one maintained definition tree, multiple harness discovery paths. The harness-visible path is not necessarily the authoring owner.
- **Jcode difference:** `SkillRegistry::load_global` already loads shared `.agents/skills` after Jcode/plugin roots (`crates/jcode-base/src/skill.rs:260-285`). `import_from_external` still copies first-run Claude/Codex skills into `.jcode/skills` (`:113-145`), while `copy_skills_dir` skips existing destinations (`:189-203`). This is not evidence that Jcode lacks shared-store support.
- **Bounded adoption:** enrich the existing provenance work with explicit canonical-target versus discovery-path wording. Show an imported copy as a copy, not as a live projection. No automatic relocation, deletion or replacement of user skill stores.
- **Acceptance:** discover a skill through a relative harness-root link, edit the canonical file, refresh, then inspect its body/source in the actual TUI. A copied import must not claim live linkage or an upstream owner that was not recorded. Include local and remote sessions and legacy unknown metadata.
- **Dedupe:** `show-skill-and-mcp-provenance/proposal.md:17-24` already owns resolved paths, roots, symlink state and display-only behavior. Archived `archive/2026-10-20-improve-workflow-suite/proposal.md:30-32` already separates canonical skill authoring from consumer copies. Extend those concepts, do not create another shared-skill-store proposal.
- **Confidence:** high source fit, medium value beyond existing scope. No migration recommended.

## 2. Treat harness aliases as aliases, not independent implementations
- **Source:** same pinned `.claude/skills -> ../.agents/skills` projection. Multiple visible paths resolve to the same definition without copying its bytes.
- **Mechanism:** separate discovery identity from implementation identity. This is an adoption inference from the link, not a claim that Sandcastle supplies a canonical-identity registry.
- **Jcode difference:** project discovery loops over `.jcode`, `.agents`, `.claude`, creates a fresh canonical `visited` set for each root, then inserts by frontmatter name (`crates/jcode-base/src/skill.rs:350-356,366-391`). Canonical cycle guards exist, but their scope does not by itself prevent the same target from being rediscovered through another root. Global insertion also replaces same-name entries (`:527-541`). `Skill` currently stores one `path`, not alias/shadow history (`:16-25`).
- **Bounded adoption:** in provenance metadata, distinguish an alias to the same canonical skill from a genuinely different same-name skill. Preserve existing winner/invocation precedence, and retain discovery aliases rather than silently erasing their origin. No new trust tier or authority from canonicalization.
- **Acceptance:** `.agents/skills/foo` plus `.claude/skills` pointing to that root yields one callable `foo`, with alias evidence available in details. A different `.claude/skills/foo` remains a real override. Test link chains, cycles, broken links, refresh after retargeting and remote serialization. Never hide a real override merely because names match.
- **Dedupe:** resolved path/symlink/shadow roots already belong to `show-skill-and-mcp-provenance`; this adds a sharper alias-versus-shadow acceptance case. `add-typed-skill-selector-metadata` remains the row/description owner.
- **Confidence:** high code evidence, medium adoption priority. This is a test/detail refinement, not a separate feature.

## 3. Separate validation of projection entries from validation of target content
- **Source:** pinned commit, `lint-staged.config.mjs:1,7-15`: `lstatSync`, `formattable(files)`, `!lstatSync(file).isSymbolicLink()`, and `if (real.length === 0) return []`. Symlinks are filtered before Prettier because formatting them fails.
- **Mechanism:** inspect the filesystem entry itself before handing it to a content processor. Link metadata and target content have different validation needs.
- **Jcode difference:** discovery deliberately follows skill links with canonical cycle/depth guards (`crates/jcode-base/src/skill.rs:363-377`), while parsing reads the target content (`:561-565`). Planned name/folder lint compares folder and frontmatter name and remains nonblocking (`openspec/changes/lint-skill-name-and-folder/specs/skill-name-lint/spec.md:3-12`), but those scenarios do not settle alias-folder semantics.
- **Bounded adoption:** add link-aware lint acceptance cases to the existing lint/provenance changes. A root projection must not create a false mismatch warning. For a renamed per-skill alias, make the discovery-folder mismatch explicit and show the canonical target separately, while still loading under frontmatter name. Validate target content even when an entry is a link.
- **Acceptance:** root projection with matching target name gives no warning; `alias -> canonical/foo` with frontmatter `foo` produces the documented alias-name warning without blocking invocation; malformed target content still fails normal parsing; broken/cyclic links terminate safely. Retain single-row rendering and control-character sanitization at widths 0/1/20/40/80.
- **Dedupe:** `lint-skill-name-and-folder` owns mismatch warnings, `show-skill-and-mcp-provenance` owns link/source details. No formatter integration proposal.
- **Do not adopt literally:** skipping symlinks in a formatter is not permission to skip validation or trust checks for linked skill bodies. Sandcastle's snippet is a formatting workaround, not a security boundary.
- **Confidence:** high source/code evidence, medium fit. The useful transfer is the validation split, not the JavaScript implementation.

- No evidenced native-tool or MCP-discovery mechanism to recommend from these caches. Keep `discover-native-and-mcp-capabilities` as the existing owner of read-only tool listing and non-starting lazy-server discovery.

- The three mechanisms are related packaging lessons from one pinned change, not three independent Sandcastle discovery subsystems. P02 gets bounded provenance/lint test refinements, not a new platform or feature family.
- **Blockers:** current Sandcastle HEAD/runtime unverified; no new retrieval needed for these bounded findings. First-run copy provenance is unavailable unless recorded, so display unknown rather than fabricate upstream lineage.
