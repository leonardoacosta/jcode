## 1. Provider-scoped env maps with explicit precedence
- **Mechanism:** `AgentProvider.env` is a `Record<string,string>`; `claudeCode`, `codex`, `pi`, `cursor` expose `options?.env ?? {}`. Source cache: 4948-4958, 5948-5958, 6362-6372, 7472-7482.
- **Documented integration:** [README, provider env](https://github.com/mattpocock/sandcastle/tree/a53e227250fb51df0ad54155b85fecc1c090c937#provider-env) says precedence is sandbox → env resolver → agent, last wins. Resolver implementation was not inspected. It documents selective `passthrough` and a distinct `CLAUDE_CODE_OAUTH_TOKEN` flow.
- **Jcode difference:** Jcode already has credential diagnostics, not merely a subprocess env map. `crates/jcode-provider-doctor/src/provider_e2e.rs:396-427` rejects missing live credentials and records an env-variable source label without its value. Do not replace native credential resolution with Sandcastle's CLI-forwarding design.
- **Bounded adoption:** Add provenance/precedence acceptance cases to the existing auth-classification and doctor-coverage changes: selected provider/account, credential source *kind*, collision outcome, and no secret values. Only scoped credential forwarding where an existing CLI adapter requires it, not arbitrary repository-supplied provider overrides.
- **Checks:** Inject conflicting synthetic sources and verify deterministic selection; unrelated provider secrets remain absent; diagnostic/error/stream logs contain no sentinel secret; retry/refresh does not change provider or account silently. Live revoked-token checks remain separately gated.
- **Dedupe:** Enrich `classify-provider-auth-failures` and `report-provider-doctor-coverage`, not a new feature. Confidence: high mechanism, medium integration because resolver code was not read.

## 2. Per-model-call context snapshots, not cumulative billing counters
- **Mechanism:** `contextWindowEvent` accepts a numeric input plus separate cache buckets, emits only positive totals, and otherwise emits nothing. `parseClaudeContextWindow` adds uncached input, cache creation, cache read; pi uses `parsePiStreamLine` with input/cacheRead/cacheWrite; OpenCode uses one `step_finish` model call, not the whole turn. Cache: 4270-4340, 5804-5824, 6618-6632.
- **Additional mechanism:** `parseCodexSessionContextWindow` scans the JSONL tail for the last `event_msg/token_count`, reads `last_token_usage.total_tokens`, and ignores a partial trailing line. Cache: 6100-6150. This is session-scoped recovery evidence, not a provider-spend ledger.
- **Jcode difference:** `crates/jcode-app-core/src/agent/turn_streaming_mpsc.rs:852-874` replaces each reported usage bucket; `:1222-1237` stores `last_usage` and provider/model identity; `:1183-1203` computes effective context usage and emits optional cache buckets. These consumers require distinct semantic checks.
- **Bounded adoption:** Within `reconcile-usage-budget-accounting`, write provider-specific normalization contracts that distinguish per-request context, cumulative turn spend, and incremental billable usage. Before changing context normalization, establish whether each adapter's input bucket already includes cache tokens. Session-tail recovery applies only to an existing CLI/session adapter that lacks the live datum.
- **Checks:** Replay multi-call tool turns with cached/uncached buckets, duplicate usage events, cumulative totals, and resumed sessions. Context must not grow merely because calls accumulate; spend must include every charged call exactly once. Tail parsing must reject malformed/foreign-session records and tolerate incomplete tails. Verify against provider transcripts, not just hand-made fixtures.
- **Dedupe:** Acceptance-detail addition to `reconcile-usage-budget-accounting`. Preserve the shared usage-bar renderer. Confidence: high source mechanism, medium provider parity pending real transcript checks.

## 3. Explicitly unsupported telemetry rather than fabricated precision
- **Mechanism:** Sandcastle intentionally emits no Cursor `context_window` event: its result usage sums the turn, which is not the final prompt footprint. It also rejects using Codex live `total_token_usage` as context because it is cumulative; the session parser reads last-call usage instead. Cache: 4784-4800 and 6100-6148; same [AgentProvider.ts source](https://github.com/mattpocock/sandcastle/blob/main/src/AgentProvider.ts).
- **Jcode difference:** `crates/jcode-app-core/src/agent/turn_streaming_mpsc.rs:1223-1228` writes absent input/output as zero, while `:1193-1203` emits a usage event only when some bucket exists. These snippets do not establish that Jcode's UI mislabels the result, but they identify where missing/reporting semantics must be traced.
- **Bounded adoption:** Extend doctor/accounting output with explicit availability and semantics: measured per-call, cumulative-only, estimated, unavailable. Preserve raw optional fields in the accounting boundary. Do not turn an unavailable number into a successful hard monetary limit.
- **Checks:** A provider without usage reporting remains marked unavailable, not zero spend; estimate-only providers never claim enforced monetary caps; unknown telemetry appears in coverage output. Interruption/cancellation must retain an unknown-final-charge state until reconciled, rather than refund a real call.
- **Jcode counterexample:** `crates/jcode-provider-core/src/provider_call_budget.rs:15-39,54-105` already enforces a shared nonrefundable call-count budget with file locking and inherited task context. Keep this hard call limit distinct from token/dollar estimates. Sandcastle evidence does not justify replacing it.
- **Dedupe:** Enrich `report-provider-doctor-coverage` plus `reconcile-usage-budget-accounting`. Confidence: high mechanism, medium proposed UI/accounting impact because downstream rendering was not audited.
