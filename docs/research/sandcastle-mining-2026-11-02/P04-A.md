## 1. Validate machine-readable planner output before dispatch
- **Mechanism:** `PlanSchema = z.object({issues: z.array(z.object({number, title, branch}))})`; extract `<plan>` from planner stdout, reject missing tags, then `JSON.parse` and `PlanSchema.parse` before starting workers.
- **Jcode difference:** dispatch already goes through native `CommAssignNext`, not a regex over planner prose (`crates/jcode-app-core/src/tool/communicate.rs:3097-3140`). Report/ownership data are native structures (`crates/jcode-app-core/src/server/state.rs:204-234`); `PlanItem` already has `file_scope`, `blocked_by`, and `assigned_to` (`crates/jcode-plan/src/lib.rs:18-31`). The current handoff proposal explicitly adds revision/check/budget fields, so this is reinforcement of existing work, not a new schema gap.
- **Bounded adoption:** retain Jcode's native plan graph. At assignment, bind the existing task ID, explicit scope, acceptance checks and dependency context into the executable handoff. Validate required fields before any worker creation. Do not introduce an XML/JSON extraction layer or Sandcastle's issue/branch assumptions.
- **Acceptance:** missing scope or invalid task reference fails before spawn; scope/checks survive assignment to an idle worker and fresh spawn; a worker report is attributable to that assigned task, not just a friendly name; blocked dependencies never dispatch.
- **Dedupe:** refine `openspec/changes/add-swarm-handoff-contracts/proposal.md:14-18` and `openspec/changes/add-swarm-handoff-contracts/tasks.md:3-6`; reuse file ownership from `openspec/changes/add-swarm-file-claims/proposal.md:11-16`. No separate “typed planner” proposal.
- **Confidence:** high on observed mechanism and overlap; medium on exact missing fields until the handoff contract is finalized.

## 2. Hold one work-item lifecycle slot through implementation and review
- **Mechanism:** `MAX_PARALLEL = 4`; FIFO `queue`, `acquire()` before `try`; `await using sandbox = await sandcastle.createSandbox(...)`; implementation then reviewer use the same sandbox; `finally { release(); }` executes after that scope, including rejection paths.
- **Jcode difference:** `coordination_in_flight_count` counts the maximum of active graph nodes and eligible running members (`crates/jcode-app-core/src/tool/communicate.rs:122-142`). `fill_slots` applies a numeric cap and computes available slots (`crates/jcode-app-core/src/tool/communicate.rs:3134-3156`). The archived recovery proposal describes reload reconciliation, not a Sandcastle disposable-sandbox slot (`openspec/changes/archive/2026-11-02-recover-swarm-workers-after-reload/proposal.md:11-21`).
- **Bounded adoption:** adopt the lifecycle invariant, not a new sandbox/worktree system: an assigned work item must not free dispatch capacity merely because its implementer reported while a required continuation/review still owns that same work. Reuse graph dependencies and native ownership. Do not keep idle completed workers artificially “running.”
- **Acceptance:** cap=2 with implement→review dependencies never starts a third active lifecycle if that policy is selected; failed spawn, failed reviewer, cancellation and timeout each release once; reload neither leaks capacity nor redispatches an in-flight task; unrelated attached human sessions remain excluded.
- **Dedupe:** reload/lease parts already belong to archived `openspec/changes/archive/2026-11-02-recover-swarm-workers-after-reload/proposal.md:11-21`; visibility belongs to `openspec/changes/surface-worker-stall-and-block-reasons/proposal.md:11-16`. Remaining cross-step slot semantics require a coordinator policy decision before becoming a requirement, not a new recovery proposal.
- **Confidence:** high on source structure; medium on fit. Jcode may correctly choose per-task rather than per-chain concurrency.

## 3. Drain parallel outcomes and preserve per-item failure identity
- **Mechanism:** `Promise.allSettled(issues.map(...))` drains all work; each rejection logs `issues[i].number`, `issues[i].branch` and its reason. Successful results remain tied to their issue by the same index before later aggregation.
- **Jcode difference:** native member data already retains the latest explicit completion report and coordinator identity (`crates/jcode-app-core/src/server/state.rs:224-234`). Await fetches reports and renders them with member outcomes (`crates/jcode-app-core/src/tool/communicate.rs:3440-3470`). Archived report work explicitly covers ready-without-report and stopped-after-report semantics. This is not evidence of a missing all-settled implementation.
- **Bounded adoption:** add an acceptance matrix for existing report/await surfaces: always return an explicit outcome for each targeted task/session and retain sibling success when one worker fails. Use stable IDs rather than Sandcastle's positional indexing. Preserve intentional systemic-auth pause behavior (`crates/jcode-app-core/src/tool/communicate.rs:1035-1092`), rather than insisting every failure is independent.
- **Acceptance:** run success + failure + blocked + report-then-stop siblings; await returns each full report/error with correct task/session identity; one local failure does not cancel unrelated work; a ready worker without report is incomplete; stopped-after-report does not trigger a false timeout; no stalled dependent task is mislabeled success.
- **Dedupe:** mostly existing archived `openspec/changes/archive/2026-11-02-return-full-swarm-reports/proposal.md:11-15`; current blocked-reason proposal owns remaining UI evidence. Add integration checks there, not another report transport.
- **Confidence:** high. Sandcastle example supplies a useful test pattern, not proof of any Jcode defect.

## 4. Separate eligibility, review completion and integration authorization
- **Mechanism:** reviewer runs only when `result.commits.length > 0`; `completedIssues` selects fulfilled runs with commits; only selected branches enter a separate `Merger` run. `MAX_ITERATIONS = 10` and empty `issues` provide explicit outer-loop bounds.
- **Jcode difference:** structured report tool arguments include validation independently of code production (`crates/jcode-app-core/src/tool/communicate.rs:2065-2090`). P04 explicitly requires attributable evidence, not commit counting (`docs/plans/PRODUCT_ROADMAP.md:155-164`).
- **Bounded adoption:** retain separate implementer/reviewer roles and an explicit integration candidate set in the handoff contract. Reject commit count as the success/review gate. Documentation-only, research and already-correct outcomes may produce no commits. A reviewer returning normally is not necessarily an approval. Merge/publication must retain existing authorization gates.
- **Acceptance:** zero-commit worker with valid requested research is accepted appropriately; commit-producing worker with failed validation is not eligible for integration; reviewer refusal cannot become approval by normal process exit; cancelled/blocked work never joins the candidate set; bounded no-work exit does not manufacture tasks.
- **Dedupe:** refine `openspec/changes/add-swarm-handoff-contracts/tasks.md:3-6`; continuation/no-work controls support P03/P05 rather than a second P04 scheduler. No auto-merge adoption.
- **Confidence:** high on the example's selection predicate; no claim that Sandcastle's unseen prompts guarantee review acceptance or safe merge.
