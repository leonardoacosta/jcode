## 1. No-adopt: empty planner output as completion
- **Source:** https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts · `PlanSchema`, `<plan>` extraction, `issues.length === 0`, `MAX_ITERATIONS`.
- Schema validation establishes issue-field shape, not completeness. An empty valid plan exits despite omitted work. Missing tags or malformed JSON fail rather than provide a semantic uncertainty verdict.
- **Jcode boundary:** `crates/jcode-todo-policy/src/followup.rs:162-210` fingerprints state, preserves final-response suppression on unchanged state, and handles incomplete todos. A planner's prose/list cannot replace these native decisions or authorize further work.
- **Fixture refinement:** keep the same unfinished required check but alternate empty/nonempty plans and persuasive final answers. Include no open todos plus a required check still missing.
- **Acceptance:** shadow disagreement never marks tasks complete, skips a check or queues another turn; missing evidence stays uncertain rather than proving completion.
- **Overlap:** `openspec/changes/admit-semantic-poke-in-shadow/specs/semantic-poke-admission/spec.md:3-12` already owns unchanged native decisions and failure handling. Add adversarial cases there, not another feature. **Confidence: high** on source behavior, proposed acceptance unrun.

## 2. No-adopt: commits or process fulfillment as progress proof
- **Source:** same `run.ts` URL · `result.commits.length > 0`, conditional reviewer invocation, `Promise.allSettled`, `completedIssues`.
- Review runs only after implementer commits; an issue becomes a completed candidate when its promise fulfills and original implementer commits exist. Successful review can be a prerequisite to fulfillment, but its returned result is discarded. Neither commits nor fulfillment proves final-artifact checks passed. Conversely a useful diagnostic or already-satisfied requirement may produce no commit.
- **Jcode boundary:** `crates/jcode-base/src/jev.rs:621-627,694-715` carries `state_revision`, `scope_ref`, `check_summary`, and generic JSON `evidence`. These are actual fields, not proof of a strongly typed progress/check provenance model.
- **Fixture refinement:** pair commit-with-failed-check against no-commit-with-new-diagnostic, holding flattering reviewer prose constant. Test a reviewer that changes the artifact after the implementer's successful check.
- **Acceptance:** no missed required check after a glowing review; diagnostic progress does not imply task completion; stale revision advice is discarded (`jev.rs:601-618`) and unchanged evidence cannot justify repeated review.
- **Overlap:** refine existing structured evidence and shadow proposals. `add-structured-continuation-evidence/specs/continuation-evidence/spec.md:3-12` covers check outcomes/redaction, not detailed artifact provenance. That binding is a proposed design refinement, not existing contract. **Confidence: high.**

## 3. Net-new refinement: account for attempted work, not loop/concurrency slots
- **Source:** same `run.ts` URL · `MAX_ITERATIONS = 10`, `MAX_PARALLEL = 4`, `acquire`/`release`, `issues.map`, `onSandboxReady: npm install && npm run build`.
- Ten planning cycles and four active issue slots do not bound tokens or total bill. Visible phases can start one planner, up to two agents per selected issue, and one merger when completed branches exist per cycle, before agent-internal calls. Merger `maxIterations: 10` is a different limit from the outer planning loop. Setup/install failures also consume time without necessarily producing commits.
- **Jcode boundary:** `crates/jcode-base/src/jev.rs:582-583,631-648,654-692,717-722` caps each evaluator at 48 accepted attempts and 600 seconds. Counter increments before provider evaluation, so failures count; rebuilding the evaluator creates a new counter/time origin. `:257-270` uses explicit routing, no HTTP retry and a two-second client timeout. These are not measured session-wide cost guarantees.
- **Fixture refinement:** distinguish attempted requests, completed verdicts, errors, setup time and hypothetical avoided native turns. Exercise a dropped result, timeout, evaluator recreation and repeated unchanged evidence.
- **Acceptance:** no savings claim from lower concurrency; failed attempts remain visible; restart/recreation cannot silently present reset evaluator counters as lifetime usage. Runtime accounting design remains unverified.
- **Overlap:** `admit-semantic-poke-in-shadow/proposal.md:14-22` already requires call/latency reporting and forbids savings claims. Add accounting/recreation cases, not a new cost subsystem. **Confidence: high** on local counter scope, medium on the appropriate session budget design.

## 4. Net-new refinement: reused worktree state must invalidate stale success
- **Actual source:** https://github.com/mattpocock/sandcastle/blob/main/docs/adr/0003-reuse-worktree-by-default.md · “Decision”, clean/dirty reuse and safe fast-forward rules. Cached as `jcode-sandcastle-worktree-adr-20261102.md` despite its ambiguous filename.
- ADR reuses dirty worktrees with a warning, keeps unpushed/diverged work, and skips refresh on fetch failure. This preserves user work but means a rerun need not begin from the same artifact. It explicitly rejects destructive refresh. Documentation describes intent, not tested runtime behavior.
- **Jcode boundary:** shadow advice binds to case/revision (`crates/jcode-base/src/jev.rs:601-618`); `observe` abstains when revision, scope or check summary is absent (`:659-678`). Presence of arbitrary summary JSON alone does not authenticate a check or bind it to changed files.
- **Fixture refinement:** replay prior success after dirty edits, a safe fast-forward, an offline rerun, and an agent-written “PASS” artifact. Native provenance must distinguish actual check observations from agent-controlled text.
- **Acceptance:** changed artifact plus stale check cannot suppress required verification; uncertain provenance does not erase dirty work, reset a branch, trigger fetch/push or authorize workspace changes.
- **Overlap:** existing structured evidence/shadow scope. Worktree policy itself belongs outside P03. No new containers/worktrees/reviewer agents. **Confidence: high** on cached ADR intent, medium on eventual provenance implementation.
