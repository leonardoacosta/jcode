# P07 · Lens B · Memory/context/privacy

## Verdict and evidence limits
- **Fit: narrow.** Sandcastle contributes boundary counterexamples, not a replacement memory architecture. P07 requires useful context without stale recall, cross-workspace leakage, unbounded disclosure or prompt growth (`docs/plans/PRODUCT_ROADMAP.md:199-213`).
- Research only. No runtime tests, installs, network retrieval, source uploads, branches, commits or implementation. Only this report authored.
- **Stale public evidence:** `~/.firecrawl/skull-mine-mattpocock-sandcastle.json`, Oct 28 snapshot, documents public `main`; newer behavior is unverified. Source anchors below describe documentation, not demonstrated runtime guarantees.
- **Pinned code evidence:** `~/.firecrawl/skull-mine-detail-sandcastle-docker.json` contains [`src/sandboxes/docker.ts` at `a53e227250fb51df0ad54155b85fecc1c090c937`](https://github.com/mattpocock/sandcastle/blob/a53e227250fb51df0ad54155b85fecc1c090c937/src/sandboxes/docker.ts). Nov 2 cached run/config/worktree pages reviewed, but not treated as proof of memory behavior.

## 1. No-adopt: executable substitutions in recalled or third-party context
- Sandcastle documents parallel ``!`command` `` expansion inside the sandbox after readiness hooks, failing the run on nonzero exit: [dynamic context](https://github.com/mattpocock/sandcastle#dynamic-context-with-command), cached markdown lines 701-719.
- Counterexample to an overly broad injection claim: [prompt arguments](https://github.com/mattpocock/sandcastle#prompt-arguments-with-key), lines 742-750, explicitly says command-like text introduced by argument values stays inert. Do not call that a confirmed execution vulnerability.
- Still reject copying this mechanism into Jcode's passive memory/instruction ingestion. A trusted template containing shell syntax is a different authority boundary from retrieved prose. Parallel expansion also permits large combined output and concurrent command cost; this source section establishes no output ceiling.
- Jcode already limits relevance inputs to 8,000 chars, 12 messages and 1,200 chars/block (`crates/jcode-base/src/memory_prompt.rs:1-5,14-25`). These are relevance-input limits, not proof that every final prompt section is bounded.
- **Bounded adoption:** add negative fixtures, not an interpolation engine. Recalled memory and instruction text containing command syntax must remain literal. If a future explicit context collector exists, preserve source/trust metadata and separate command authorization from text loading.
- **Acceptance:** malicious recall text creates no process; nested substitution in an argument stays inert; oversized parallel results and hanging collectors have aggregate byte/time limits before provider submission. Last two checks apply only if collectors are introduced.
- **Overlap:** extend `add-prompt-budget-ratchet/proposal.md:9-18` and archived `native-instruction-file-loading`, not a new dynamic-context feature. Confidence: high for no-adopt, medium for untested future collector checks.

## 2. No-adopt: automatic transcript export as harmless sandbox cleanup
- [Session capture](https://github.com/mattpocock/sandcastle#session-capture), cached lines 1042-1050, documents automatic resumable-session copy to host paths, including provider-specific transcripts. [`IterationResult`](https://github.com/mattpocock/sandcastle#iterationresult) exposes `sessionFilePath`; [session resume](https://github.com/mattpocock/sandcastle#session-resume) reuses captured history.
- Deleting a container is not deleting exported history. Transcript copies can preserve secrets, stale instructions and provider output beyond sandbox lifetime. This is a persistence counterexample, not evidence Sandcastle lacks all deletion controls.
- Jcode stores memory separately: project-path hash files (`crates/jcode-base/src/memory.rs:171-180`) and global memory (`:348-354`). `MemoryManager::forget` removes graph entries (`:942-955`), not every historical transcript copy.
- **Bounded adoption:** inventory transcript/import/export copies in retention evidence; explicitly distinguish forgetting a memory from erasing past conversation/provider disclosure. Do not promise retroactive erasure.
- **Acceptance:** seed a synthetic canary, remove its memory, then test fresh recall and resumed-session behavior separately; report any historical appearance without calling graph deletion a failure or complete erasure. Export/import fixtures must name copy locations and retention ownership.
- **Overlap:** `add-memory-retention-controls/proposal.md:14-22` excludes session retention; archived `session-store-retention` owns session cleanup. Attach cross-boundary evidence to these owners, not duplicate purge commands.
- Confidence: high for documented export and separate Jcode stores; medium for inventory completeness. No canaries were created during research.

## 3. New test gap: host-path rewriting must not silently redefine memory identity
- Sandcastle's [session capture](https://github.com/mattpocock/sandcastle#session-capture), cached line 1046, rewrites provider `cwd` fields to the host repo root for native resume. This is useful interoperability, not a workspace authorization decision.
- Jcode's `project_memory_file` hashes the supplied project path (`crates/jcode-base/src/memory.rs:171-180`); project/global writes are explicitly separate (`:386-403`). A fresh worktree path can lose expected project continuity; blindly normalizing every imported path to the current root can attach unrelated context instead.
- **Bounded adoption:** provenance/identity regression fixtures for import/resume, not automatic path rekeying. Preserve original source identity separately from the execution path. No silent merge of project memories merely because a transcript was relocated.
- **Acceptance:** same repo via worktree, moved checkout, unrelated repo at a reused path, and imported foreign transcript each produce an explicit expected scope or safe unknown. Assert no foreign-memory injection. Which aliases should share memory remains a user/product decision.
- **Overlap warning:** `add-attributable-memory-recall/proposal.md:18-22` delegates workspace-scoped recall to `workspace-aware-context`; the latter's `proposal.md:9-15` specifies origin matching, hints, identity warnings and worker propagation, but does not explicitly specify a recall filter. This ownership gap needs reconciliation, not an inferred completed boundary.
- Confidence: high for path-key mechanism and proposal mismatch; medium for migration relevance. No actual cross-workspace leak reproduced.

## 4. No-adopt: filesystem isolation as evidence of context privacy
- Pinned `docker` factory calls `resolveUserMounts`, merges `createOptions.mounts` with user mounts, preserves mount `readonly`, and registers `docker rm -f` cleanup (`src/sandboxes/docker.ts`; cached markdown lines 1212-1228,1258-1266,1388-1412). These are concrete filesystem/lifecycle mechanisms, not semantic retrieval filters.
- Sandcastle also documents sandbox `env`, mounts and network options under [sandbox providers](https://github.com/mattpocock/sandcastle#sandbox-providers). Read-only access still permits reading and disclosing content. Container removal cannot revoke context already sent to a model.
- **Bounded adoption:** a boundary matrix in P07 verification: filesystem access, project/global retrieval scope, provider submission, and persistence. Record each independently. Do not infer one from another or add a new sandbox/memory service.
- **Acceptance:** deny an unapproved-workspace canary at retrieval and inspect the actual outgoing provider payload; separately verify a permitted read-only file remains readable but unwritable. An authorized local test must use a controlled provider seam or approved destination, not disclose a real private canary.
- **Overlap:** P06 owns provider/auth/budget reliability; P07 owns context-selection/disclosure evidence. Filesystem isolation needs its own execution-boundary checks. `add-attributable-memory-recall` and `workspace-aware-context` are the integration points. Confidence: high for boundary distinction; no Sandcastle or Jcode runtime security claim made.

## Dedupe, confidence, blockers
- Do not propose a new memory service, generic context budgets, bulk memory purge, native instruction loader, or session GC: current P07 proposals/archive already own those outcomes. `add-compaction-quality-evidence` remains the compaction owner; no Sandcastle compaction-quality mechanism established here.
- Strongest net-new contribution: import/resume identity fixtures plus the explicit workspace-recall ownership gap. Other findings are no-adopt decisions and acceptance refinements.
- Blockers for implementation readiness only: intended cross-worktree memory identity; confirmed recall-filter owner; current Sandcastle runtime/version evidence if claiming parity. None blocks this research deliverable.
- Validation: checked current local source/proposal paths and line anchors, compared active and archived P07 owners, and distinguished pinned code from stale README evidence. No tests run because no implementation was requested.
