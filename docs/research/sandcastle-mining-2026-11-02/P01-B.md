## 1. No-adopt: commits as completion or merger eligibility
- S1 `completedIssues` admits fulfilled implementer results with `commits.length > 0`; reviewer return values are not retained in that selection.
- Counterexample: an implementer commits failing code; a reviewer returns normally while reporting a blocker. The visible selection still admits that branch.
- This is not proof that Sandcastle's lower-level runtime ignores validation. It is evidence that this sample's visible predicate does not establish acceptance.
- Existing owner: `openspec/changes/bind-acceptance-evidence-to-runtime/proposal.md:14-23` covers runtime identity, not review verdicts or CI integration.
- Bounded candidate: test completion admission against explicit gate/review outcomes bound to the final diff, rather than commit presence. Keep runtime identity work in its existing proposal.
- Acceptance: committed failure, reviewer blocker, missing gate evidence, or evidence for an older diff cannot produce a verified-complete result; a verified no-code outcome must not fail solely for lacking commits.
- Confidence: high for sample predicate, medium for adoption scope pending current admission-path tracing.

## 2. No-adopt: reviewer invocation as independent approval
- S1 launches a named reviewer only after commits, using the same configured `claude-opus-4-8` model as the implementer. Naming a run “Reviewer” does not prove independence, evidence quality, or permission to continue.
- Existing owner: `openspec/changes/admit-judge-feedback-with-bounds/proposal.md:12-23` already addresses advisory content, one admitted DM, continuation caps, and display-only `/review`.
- Jcode evidence: `crates/jcode-tui/src/tui/app/commands_review.rs:514-545` supplies judge response instructions as prompt text.
- Net-new test angle: reviewer availability and review validity are separate states. A successful tool invocation with no verdict must not count as a completed review.
- Acceptance: empty/malformed review, unrelated commit reference, duplicate DM, and contradictory STOP/CONTINUE responses cannot silently approve completion or authorize a remote action.
- Cost: reusing a model is not inherently invalid; requiring a different provider would add cost and credentials without proving independence. Do not impose that rule.
- Confidence: high for duplication boundary; medium for broader review-record design.

## 3. No-adopt: parsing a planner result as execution authority
- S1 validates `<plan>` JSON with `PlanSchema` and immediately uses returned issue branches to create sandboxes. Schema validity says nothing about whether the user authorized implementation or merges.
- S2 documents plan → implement → review → merge sequencing. That is a repository-specific automation contract, not a permission grant for Jcode.
- Existing owner: `openspec/changes/restrict-plan-command-execution/proposal.md:14-23,31-33` already proposes enforced read-only native tools and acknowledges MCP classification is outside scope.
- Jcode evidence: `crates/jcode-tui/src/tui/app/commands_plan.rs:27-46` expresses plan-only restrictions in the generated prompt.
- Net-new acceptance angle: a structurally valid plan containing branch names, issue IDs, or shell commands must remain inert until separately admitted for execution. Tool-result or issue-text instructions cannot supply that authority.
- Security: prompt-only restrictions cannot establish safety against arbitrary model output. Do not expand the existing proposal into general sandbox/MCP security under P01.
- Confidence: high.

## 4. Candidate: preserve partial-failure evidence without failure amplification
- S1 uses `Promise.allSettled` so sibling work survives a rejected issue, then logs rejected outcomes through `console.error`. This is useful isolation, but those log lines alone are not durable acceptance records.
- P01 owns evidence meaning; process reattachment belongs elsewhere. `docs/plans/PRODUCT_ROADMAP.md:94-103` does not justify rebuilding the worker scheduler.
- Bounded adoption: preserve distinct succeeded/failed/unknown outcomes and reason references when aggregating an already-existing multi-task run. Do not infer “all done” from the successful subset.
- Acceptance: one success plus one failure retains both outcomes across aggregate reporting; a lost review result stays unknown; cancellation is not success. Redact secrets from reasons before storing/showing them.
- Cost: S1 limits outer loops to 10 and active issues to 4, but issue count and call duration are not visibly bounded there. Those constants do not prove a spend ceiling. Avoid copying the loop as a budget control.
- Confidence: medium; requires tracing current result persistence before proposing any new artifact.

## 5. No-adopt: warm-worktree reuse as reproducible verification
- S4 deliberately reuses existing worktrees and preserves untracked files, dependencies, and caches. This improves iteration speed but permits stale generated files or previous-run outputs to influence a check.
- S1 also copies `.sandcastle`, `node_modules`, and `tsconfig.json` into worker worktrees. S3 runs `pnpm install && pnpm build` during setup and exposes configured GitHub credentials to sandbox jobs.
- Counterexample: the same source commit passes only with a leftover generated file. Commit identity alone does not establish reproducibility; copying credentials also makes a clean-looking review sandbox consequential.
- Existing owner: runtime identity binding remains `openspec/changes/bind-acceptance-evidence-to-runtime/proposal.md:16-23`; its non-scope explicitly excludes CI and artifact storage.
- Net-new evidence angle: label a validation as warm/reused versus clean and record dirty/untracked-input presence without collecting file contents or credentials. Reserve environment-reproducibility design for its proper phase.
- Acceptance: a reused worktree cannot be reported as clean merely because tracked files match HEAD; no environment values appear in evidence. Do not automatically delete user files or provision credentials to obtain a clean label.
- Confidence: high for documented reuse, medium for proposed provenance field value.
