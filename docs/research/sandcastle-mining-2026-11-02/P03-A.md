## 1. Validate model output before selecting further work
- Sandcastle: `PlanSchema`, extraction of `<plan>`, `JSON.parse`, and `PlanSchema.parse` establish a typed boundary. Missing tag throws; an empty `issues` array exits the outer loop. This is structural validation, not proof that selected issues are authorized or complete.
- Jcode: `TodoSnapshot` and `FollowUpPolicy` already provide a typed deterministic decision surface (`crates/jcode-todo-policy/src/followup.rs:28-42,109-121`), while the proposed semantic result is `continue`/`stop`/`uncertain` (`openspec/changes/admit-semantic-poke-in-shadow/proposal.md:14-16`).
- Bounded adoption: use Sandcastle's validate-before-branching pattern for the shadow observer response. Do not import its crash-on-bad-planner-output behavior into the TUI: malformed/absent semantic results must leave the deterministic decision unchanged.
- Acceptance refinement: missing tag-equivalent field, invalid enum, oversized response, and prose-only success yield invalid/uncertain observations with no queued turn, cancellation change, or budget reset attributable to the observer.
- Dedupe: belongs under `admit-semantic-poke-in-shadow` and `route-jev-supervision-explicitly`, not a new feature. Confidence: high on source mechanism; medium on incremental coverage value until their final tests are checked.

## 2. Keep reviewer context tied to the work actually produced
- Sandcastle: `await using sandbox = await sandcastle.createSandbox(...)` encloses both `sandbox.run` calls. `Implementer` runs first; `Reviewer` runs in the same sandbox only if `result.commits.length > 0`. Both receive the same issue number/title/branch.
- Jcode: current follow-up fingerprints serialize todos/plan/goals, not repository revisions or actual check output (`crates/jcode-todo-policy/src/followup.rs:174-186`). Planned structured evidence records required-check observations (`openspec/changes/add-structured-continuation-evidence/proposal.md:14-16`).
- Bounded adoption: attach native, redacted work/check provenance to each semantic observation so Jev judges the relevant work, rather than an agent's final narrative. Reuse the P01 acceptance-evidence work rather than create a parallel evidence store.
- Acceptance refinement: a passing check from revision A cannot satisfy unfinished required checks after revision B. Also test successful no-commit work: inspection, explanation, and local uncommitted fixes must not become invisible merely because `commits.length == 0`.
- No-adopt: commit presence as completion or reviewer-eligibility authority. Sandcastle's branch workflow uses it as a heuristic; Jcode's general task scope cannot.
- Dedupe: refinement of `add-structured-continuation-evidence` plus P01 `bind-acceptance-evidence-to-runtime`. Confidence: high on same-sandbox sequencing; medium on the smallest provenance representation.

## 3. Preserve independent failure outcomes instead of collapsing a batch
- Sandcastle: `Promise.allSettled` retains one outcome per issue; rejected outcomes log the original issue/branch and reason. `completedIssues` separately filters fulfilled results with commits before constructing merger inputs.
- Jcode: `TodoSnapshot` primarily describes task state (`crates/jcode-todo-policy/src/followup.rs:28-42`); structured evidence explicitly adds observed check results and wait/blocked markers (`openspec/changes/add-structured-continuation-evidence/proposal.md:14-16`).
- Bounded adoption: preserve native operation identity and pass/fail/not-run distinctions when summarizing concurrent required checks. A successful sibling must not erase a failed or unresolved required check. Feed only bounded summaries to Jev.
- Acceptance refinement: matched replay with one passing check and one failed check must retain the failed obligation; a rejected operation, pending operation, and genuine blocked dependency must remain distinguishable. An optional check failure must not invent a required obligation.
- No-adopt: Sandcastle's `fulfilled && commits.length > 0` filter as proof of verified completion. The source does not inspect a structured reviewer verdict here.
- Dedupe: test/data-shape refinement within `add-structured-continuation-evidence` and `admit-semantic-poke-in-shadow`. Confidence: high on source distinction; medium on new value beyond existing proposal requirements.

## 4. Bound nested loops separately and release capacity on failure
- Sandcastle: `MAX_ITERATIONS = 10` bounds planning rounds; `MAX_PARALLEL = 4`, `acquire`, `release`, and `finally` bound concurrent issue work; merger `maxIterations: 10` bounds its own iteration loop. These are distinct bounds, not a documented global token/spend ceiling.
- Jcode: `MAX_GATE_ATTEMPTS = 5`, `gate_attempts`, and stored fingerprints already constrain deterministic follow-up (`crates/jcode-todo-policy/src/followup.rs:24-26,111-120,174-186`). The live tree also already contains `JevPurpose::Supervision` and a two-second supervision observation timeout (`crates/jcode-base/src/jev.rs:50-75,355-365`).
- Bounded adoption: retain native gate caps while separately accounting for semantic calls, timeout/uncertainty, and replay cost. An observer timeout must release any observer slot and must not replenish the follow-up budget.
- Acceptance refinement: repeated timeouts, unchanged wait evidence, and repeated semantic `continue` responses cannot exceed native eligibility/caps. Cancellation during observation prevents a later response from queueing work. Record call count and latency separately from turns.
- Dedupe: existing P03 routing/shadow proposals already own this direction. Add failure-path acceptance cases only if absent. Confidence: high on caps/timeout mechanisms; no claim of measured savings.
