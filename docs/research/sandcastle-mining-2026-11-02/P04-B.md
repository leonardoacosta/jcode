# P04-B: Sandcastle fit, counterexamples and no-adopt decisions

Research only. Owner: P04 lens B. No implementation or new OpenSpec proposal.

## Evidence and phase fit
- P04 requires attributable executable scope, dependencies, ownership, recovery and coordinator verification, not merely parallel agents (`docs/plans/PRODUCT_ROADMAP.md:153-165`).
- Public source A: [`.sandcastle/run.ts`](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), cached `~/.firecrawl/jcode-sandcastle-run-20261102.md`. Evidence below is the repository's orchestration example, not proof of library guarantees or runtime acceptance.
- Public source B: [ADR 0003](https://github.com/mattpocock/sandcastle/blob/main/docs/adr/0003-reuse-worktree-by-default.md), cached `~/.firecrawl/jcode-sandcastle-worktree-adr-20261102.md`. Design intent, not implementation verification.
- Cache caveat: filename dates suggest November 2 retrieval, but references use mutable `main`, not pinned source revisions. Root repository cache is an October 28 snapshot and is stale for present-runtime claims. No network retrieval or source upload performed.
- Jcode graph spans were stale after ongoing source changes. Current source was checked directly for the citations below. Existing dirty checkout was preserved.

## 1. Reject commit-count success and conditional review
- Mechanism: source A `if (result.commits.length > 0)` gates Reviewer execution. `completedIssues` selects fulfilled outcomes with commits; `completedBranches` then feeds a Merger run. Cache lines 558-580, 610-676.
- Counterexamples: valid research/no-change tasks produce zero commits; a committed broken patch passes the selection filter; the reviewer result is not inspected in this script before the original implementer result is returned. A fulfilled call is not evidence that acceptance checks passed.
- Decision: do not import this success predicate, conditional review rule, or automatic merge trigger. Preserve explicit authorization and coordinator verification.
- Bounded adoption: add acceptance cases to `add-swarm-handoff-contracts`, not a second reporting feature. Record task outcome separately from commit production, retain review findings and check exit statuses, and bind evidence to the final revision.
- Jcode difference: `PlanItem` currently carries status/scope/dependencies/assignee, not acceptance evidence (`crates/jcode-plan/src/lib.rs:18-31`). Existing proposal already specifies base/head/check results (`openspec/changes/add-swarm-handoff-contracts/proposal.md:14-17`). Archived `return-full-swarm-reports` covers delivery, not proof of correctness.
- Acceptance: research with no commits can complete with attributable evidence; committed failing tests cannot pass; actionable review findings block integration; final HEAD drift invalidates earlier checks. No auto-publication.
- Confidence: high for script behavior; medium for adoption details pending contract design.

## 2. Reuse bounded slots, not the local semaphore as durable lifecycle state
- Mechanism: source A `MAX_PARALLEL = 4`, `MAX_ITERATIONS = 10`, `acquire`/`release`, `Promise.allSettled`, and `finally { release(); }`; cache lines 422-426, 482-510, 584-604.
- Fit: a failed branch need not discard successful peers. A slot must release on failure, but a hanging worker can retain it indefinitely. Four simultaneous workers limit instantaneous fanout, not tokens, dollars or total launches across ten batches.
- Decision: retain the bounded-fanout principle and add failure tests, not a new semaphore implementation. Do not treat process-local counters or `allSettled` as crash recovery, dependency semantics or a spend ceiling.
- Jcode difference: native spawn already rejects non-root callers and applies an absolute member ceiling (`crates/jcode-app-core/src/server/comm_session.rs:1430-1444`). Existing handoff proposal adds turn budgets, and `surface-worker-stall-and-block-reasons` owns stall visibility.
- Acceptance: failed/cancelled workers free capacity exactly once; one hung worker exposes a stall rather than monopolizing all progress; independent lanes proceed after peer failure; descendants of failed dependencies stay blocked; respawn cannot bypass the member ceiling or reset consumed budget silently.
- Dedupe: fold tests into handoff/stall/recovery owners. No claim that turn budgets alone impose a monetary cap.
- Confidence: high on observed mechanism, medium on untested Jcode lifecycle edges.

## 3. Reject branch names as ownership or trusted planner output
- Mechanism: source A `PlanSchema` accepts an array of `{ number, title, branch }`, parses planner JSON, then uses `issue.branch` for `createSandbox`; cache lines 412-420, 458, 518-536. The schema shown has no branch uniqueness, dependency or file-scope fields.
- Failure/security mode: duplicate branch assignments can target the same reused worktree. An agent-selected branch/title is task data, not authority to access arbitrary paths, publish work or run extra hooks. Schema shape does not establish disjoint ownership.
- Decision: no-adopt the minimal schema as an executable handoff contract. Do not infer that Sandcastle lacks validation elsewhere, which was not inspected.
- Bounded adoption: validate conflicting assignments before dispatch, retain existing native plan dependency/scope fields, and make actual file claims authoritative for concurrent edits. Do not create branch-per-worker defaults.
- Jcode difference: `PlanItem.file_scope`, `blocked_by`, `assigned_to` already exist (`crates/jcode-plan/src/lib.rs:25-30`). `add-swarm-file-claims` already owns per-session claims, conflict policy and terminal/orphan release (`openspec/changes/add-swarm-file-claims/proposal.md:11-14`).
- Acceptance: duplicated branch/workspace ownership is diagnosed before edits; disjoint lanes remain parallel; dependency cycles/failed predecessors do not launch; hostile planner strings cannot grant publication or path authority; claims remain correct through retry.
- Dedupe: handoff/claims acceptance additions only, no new scheduler proposal.
- Confidence: high for the displayed schema and overlap; medium for library-level implications.

## 4. Reject silent dirty reuse and automatic branch refresh for recovery
- Mechanism: source B removes `throwOnDuplicateWorktree` from `run()`, `createSandbox()`, `SandboxFactory`, `WorktreeManager.create`. Clean and dirty worktrees both reuse; dirty reuse warns. Clean strictly-behind branches fetch and merge `--ff-only`; dirty/diverged/offline cases continue as-is. Cache lines 92-120.
- Benefit: `--ff-only` avoids the destructive reset counterexample of clean-but-unpushed commits. Warning about reused state is useful provenance.
- Failure mode: dirty reuse still hands unrelated work to a new agent. A safe Git fast-forward can nonetheless invalidate an assignment's frozen base or prior verification. Offline continuation may operate on stale source. Worktree reuse does not establish exclusive ownership.
- Decision: do not adopt automatic worktree creation, warning-only ownership transfer, remote refresh or cleanup. These also conflict with this environment's explicit worktree/publication boundaries and persistent worktree location rules.
- Bounded adoption: surface existing workspace identity, starting revision and dirty/divergent/unknown freshness in recovery evidence. Changed-base reuse must be an explicit revalidation event, not transparent continuation.
- Jcode difference: `WorkerSpawnSpec` persists lane/prompt/model/working directory/last status, not base revision (`crates/jcode-app-core/src/server/swarm_persistence.rs:333-349`); the handoff proposal already owns `base_rev`.
- Acceptance: reload/retry preserves unrelated hunks and unpushed commits; detects changed base; makes no implicit fetch/reset/worktree mutation; offline status is explicit, not a fabricated freshness claim.
- Dedupe: extend handoff/recovery acceptance, do not reopen archived recovery as unimplemented wholesale.
- Confidence: high for ADR intent; runtime reuse behavior unverified.

## 5. Keep resource disposal separate from durable retry and evidence retention
- Mechanism: source A `await using sandbox = await sandcastle.createSandbox(...)` encloses implementer plus reviewer, followed by slot release in `finally`; cache lines 516-590. It expresses scoped resource lifetime, not a documented durable handoff protocol.
- Failure mode: abrupt process death does not prove asynchronous disposal ran. Reclaiming a slot must not erase worker evidence, dirty files or claims needed to explain a failed task. Automatic retry may duplicate work when a session survived but lost its coordinator connection.
- Decision: adopt only the lifecycle distinction: stop/reclaim, preserve evidence, then explicitly classify resumable versus orphaned. Do not infer container/worktree deletion guarantees from `await using` or add sandbox infrastructure to P04.
- Jcode difference: current recovery marks a nonterminal worker orphaned when its session is absent and records how to retry (`crates/jcode-app-core/src/server/swarm_persistence.rs:464-484`). Archived `recover-swarm-workers-after-reload` already covers persisted spawn spec and retry; claims proposal owns orphan release.
- Acceptance: kill coordinator during implementation/review, recover without duplicate spawn, preserve last report/check evidence, mark absent sessions orphaned, release claims without deleting edits, and permit bounded retry only after ownership is reconciled.
- Dedupe: lifecycle integration tests across existing recovery/claims/handoff changes, not a new persistence layer.
- Confidence: high for local orphan classification; medium for disposal implications because sandbox implementation was not executed.

## Verification and blockers
- Read P04, cached public source/ADR, current native source and active/archived overlap proposals. No runtime tests, builds, installs, login, Git mutations or private-source uploads.
- Five decisions above are acceptance refinements or explicit no-adopt decisions. Existing P04 changes own all identified mechanisms; no net-new proposal justified by this evidence.
- Blockers: no pinned upstream implementation or runtime traces, no demonstrated cleanup/crash safety, no measured token/latency/cost savings. Those need scoped follow-up before any implementation claim.
