# P05-B: Durable triage, restart and worktree policy

- Scope: `docs/plans/PRODUCT_ROADMAP.md:167-183`. P05 already owns task admission, finite limits, cancellation, restart reconciliation and worktree policy. Most mechanisms below belong in those existing changes, not new proposals.

## 1. No-adopt: model-shaped plans are not admission authority
- **Source:** S1 `PlanSchema` accepts `number: z.number()`, `title: z.string()`, `branch: z.string()`, then passes each branch to `createSandbox` and title/branch to implementation and review prompts. No readiness/evidence/authorization fields exist in this schema.
- **Failure/security:** structural parsing does not prove task readiness, scope or authorization. Duplicate tasks/branches and externally controlled issue text can cross into autonomous execution unless separately checked. This is an admission-gap example, not proof of a sandbox escape or command injection.
- **Jcode difference:** overnight instructions explicitly require proven, bounded work and disallow external effects without permission (`crates/jcode-overnight-core/src/prompts.rs:105-113`). `configure-task-and-worktree-policy/proposal.md:12-18` and `admit-overnight-tasks-on-evidence/proposal.md` already own machine-enforced admission.
- **Bounded adoption:** use this as an adversarial admission case, not as an alternate triage engine. Validate repository-bound task identity, evidence freshness, branch scope and explicit effect authority before sandbox creation. Titles remain untrusted data.
- **Acceptance:** malformed/duplicate task IDs, a noninteger issue number, stale evidence and conflicting tasks targeting one branch produce an attributable rejection before execution. Instruction-like issue titles do not expand authority. A valid bounded task still admits.
- **Overlap/confidence:** extends admission security tests, no new proposal. High confidence in visible schema and call flow. Prompt internals and sandbox internals remain uninspected.

## 2. No-adopt: process-local loop bounds as durable resource policy
- **Source:** S1 `MAX_ITERATIONS = 10`, `MAX_PARALLEL = 4`, an in-memory `running` counter and waiter queue, plus `Promise.allSettled`. Each semaphore slot spans implementation and review inside `try/finally`.
- **Counterexample:** the semaphore is reasonable for one live process. Restart loses its iteration count, queue and operation stage. Four slots also say nothing about token spend, elapsed time or heterogeneous build memory. This is not evidence that Sandcastle itself lacks other durable APIs.
- **Jcode difference:** `OvernightManifest` already persists run identity, cancellation, working directory and provider/model, but calls its agent count `max_agents_guidance` (`crates/jcode-overnight-core/src/lib.rs:47-81`). Prompt-only resource guidance remains visible at `prompts.rs:111-112`.
- **Bounded adoption:** keep a slot through verification, but persist accepted-task identity, remaining finite limits and stage in Jcode's existing run records. Reconcile ownership before admitting replacements.
- **Acceptance:** terminate after admission and after implementation, restart twice, and verify no duplicate implement/review action, no fresh budget, no expired authorization reuse, and one terminal result per admitted task. Cancel while waiting and while reviewing.
- **Overlap/confidence:** `enforce-overnight-cancellation-and-limits`, `reconcile-overnight-runs-after-restart`, `reattach-background-tasks-after-reload`; no second runtime ledger. High static confidence, no crash test performed.

## 3. No-adopt: treating a worktree path as durable repository identity
- **Source:** S2 Context describes branch worktrees at `.sandcastle/worktrees/<name>/` and explains that a reused local branch can be stale. Decision refreshes only clean, strictly-behind branches with fetch plus fast-forward. Dirty/diverged trees and fetch failures reuse the existing state.
- **Failure:** a missing, replaced or stale directory can silently change the repository being resumed. A familiar path and successful reuse are not proof of task authorization or valid base ancestry.
- **Jcode evidence:** `restore_snapshot` relaunches session IDs in a resolved directory (`crates/jcode-app-core/src/restart_snapshot.rs:184-213`). `resolve_session_cwd` falls back to the caller's current directory if the saved directory is absent (`:218-223`). This is terminal-session restoration, not proof of safe unattended task reconciliation.
- **Bounded adoption:** during autonomous-task restore, require recorded repository/worktree identity and base to match. If absent or changed, park only that task with an explicit reason. Do not globally change manual session restore from this research recommendation.
- **Acceptance:** remove the saved worktree, replace its path with another repository, change its base, and launch from a different cwd. No case may resume autonomous writes in the fallback directory. Unaffected tasks continue.
- **Overlap/confidence:** a specific acceptance refinement for `reconcile-overnight-runs-after-restart`, `configure-task-and-worktree-policy`, not a new worktree manager. High confidence in Jcode's fallback and ADR text, no runtime acceptance exercised.

## 4. No-adopt: warn-only dirty reuse and implicit origin refresh
- **Source:** S2 `WorktreeManager.create` removes `throwOnDuplicateWorktree`, reuses clean or dirty worktrees, warns for dirty state, and refreshes clean strictly-behind branches from hardcoded `origin`. Consequences explicitly place worktree locking (#401) in the future and note fetch latency.
- **Failure/security/cost:** a warning does not grant permission to overwrite another session's dirty files. A clean tree can contain unpublished commits or have a live owner. Fetch failure is nonfatal, so a reused tree cannot be labeled current without evidence. Default network refresh also adds latency and may change the base assumed by prior verification.
- **Jcode difference:** `configure-task-and-worktree-policy/proposal.md:12-23` already covers verified-default, requested-existing and explicitly-authorized isolated modes, plus permission and runtime-denial separation. That proposal is not completion evidence.
- **Bounded adoption:** reuse the ADR's staged/unstaged/untracked and behind/ahead/diverged distinctions, but require ownership and placement authorization separately. Do not import default dirty reuse, hardcoded `origin`, or refresh-as-authorization.
- **Acceptance:** dirty tracked/untracked state, unpublished commits, another live consumer, divergence and failed fetch each produce an explicit policy result. No reset, delete or automatic takeover. Any approved fast-forward invalidates old verification and records before/after base identity.
- **Overlap/confidence:** strengthen existing worktree-policy acceptance, no new lifecycle service. High confidence in ADR text, implementation and locking runtime uninspected.

## 5. No-adopt: successful reviewer invocation implies integration readiness
- **Source:** S1 awaits `sandbox.run` for the Reviewer but discards its return value, returns the Implementer's `result`, and selects `completedIssues` from fulfilled outcomes with `result.commits.length > 0`. The Merger then receives those branches. A thrown reviewer error rejects the task, but the visible code does not inspect a structured review verdict.
- **Failure/security:** completing a reviewer call is not proof that findings are resolved. Commit presence is not verification or integration authority. A crash around merger execution can also cause repeated integration attempts. The example does not bind the reviewed tree to a machine-enforced accepted verdict.
- **Jcode difference:** task-card instructions already require evidence/validation and files changed (`crates/jcode-overnight-core/src/prompts.rs:116-121`), while external-effect authority is separate (`:108`). Existing `admit-overnight-tasks-on-evidence/proposal.md` owns evidence-aware admission, and `reconcile-overnight-runs-after-restart/proposal.md` owns safe post-interruption outcomes.
- **Bounded adoption:** bind verification and accepted findings to an exact commit/tree and persist authorized integration intent/result before any resumable side effect. Preserve existing review policy rather than importing Sandcastle's reviewer topology.
- **Acceptance:** a reviewer returning actionable findings without throwing cannot produce merge-ready status. Valid verification without integration permission records verified work but performs no integration. Changed commits invalidate old results. Restart after completed integration reconciles rather than replaying blindly.
- **Overlap/confidence:** acceptance refinement across durable admission/recovery and P04 integration. High confidence in visible return/filter flow. Reviewer/Merger prompts could add safeguards, but they were not inspected and cannot count as proven gates.

## Dedupe, confidence and blockers
- Read the active P05 proposals named above and archived `2026-11-02-shared-server-crash-resilience`. Crash restart policy is not overnight run reconciliation. Do not reopen an archived feature to duplicate an active one.
- **Net-new specificity:** conflicting-branch admission rejection, missing/replaced-cwd fail-closed autonomous restore, ownership-aware dirty reuse/base freshness, and commit-bound replay-safe integration checks. Durable counters and typed admission are existing scope, not discoveries.
- **Validation:** static inspection of cached actual example/ADR plus current on-disk Jcode spans and proposal dedupe. No build/test claim, benchmark, runtime acceptance, new OpenSpec change or implementation.
- **Blockers:** graft/agentgrep indexed missing split-crate paths (`jcode-runtime-persistence-core`, `jcode-swarm-runtime-policy`) and absent proposal names, so those hits were discarded and final citations use verified live checkout files. No graph refresh authorized. Cache names are not source identity: the final cached ADR resolves to `0003-reuse-worktree-by-default.md`, so prior branching/cleanup assumptions were discarded. Uninspected prompts and sandbox internals limit conclusions about current Sandcastle runtime.
