## 1. Adopt boundary-specific credential tests, not Sandcastle's key names
- Source: cached markdown:44,56 records `fix(init): use CODEX_API_KEY in Codex .env.example template`; commit https://github.com/mattpocock/sandcastle/commit/c1463194c18c0a65c6811ce892e4d38d3598b0d9 . This is cached commit-list metadata, **not an inspected diff**. README setup at markdown:118 uses `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`.
- Mechanism/counterexample: a credential variable valid for a native API client need not authenticate a launched CLI. A generated template can look correct yet be ignored by the actual consumer.
- Jcode differs: native `load_env_api_key()` explicitly reads `OPENAI_API_KEY`, trims/ignores empty values, then uses `openai.env` (`crates/jcode-base/src/auth/codex.rs:585-594`). Blindly copying `CODEX_API_KEY` would be wrong here.
- Bounded candidate: extend existing provider-doctor/auth coverage with **credential-consumer** cases: native API versus any explicitly supported external CLI path. Test the real consumer's allowlisted variable names, empty values, wrong-provider keys, and absence of alternate ambient credentials. Do not add an external CLI path merely to test one.
- Acceptance: isolated child environments use fake sentinels offline; wrong names cannot report authenticated or fall back to another account. Separately authorized live checks identify native/CLI consumer and actual credential source without printing secrets. Offline success remains offline evidence.
- Ownership: `report-provider-doctor-coverage` plus `classify-provider-auth-failures`, not a new proposal. Confidence: high for Jcode mismatch, medium for Sandcastle historical cause.

## 2. Adopt collision detection narrowly; reject wholesale environment merging
- Source: https://github.com/mattpocock/sandcastle#provider-env ; `claudeCode(..., { env })`, `docker({ env })`, `run()` at cached markdown:1173-1193. Documented rules: explicit provider env overrides `.sandcastle/.env`; agent/sandbox key overlap throws; ambient `process.env` also participates.
- Risk: conflict detection between two explicit maps does not prove narrow credential exposure or identify which ambient/file credential wins. A sandbox infrastructure token and model token have different recipients. A project-controlled `.env` is not authority to change provider identity.
- Jcode already models environment, app-config, and trusted-external credential origins (`crates/jcode-base/src/auth/mod.rs:1320-1348`). Its multiple-source design is not equivalent to a single dotenv merge.
- Bounded candidate: add a **source-conflict/provenance matrix** to existing auth work, retaining current supported precedence. Check conflicting ambient/config/external sources, explicit account selection, and refresh cancellation. Reject cross-recipient credential forwarding in any future sandbox adapter unless explicitly required and authorized.
- Acceptance: competing fake keys resolve to a documented source/account, diagnostics disclose source category only, unrelated keys never reach the target process, cancelled refresh preserves the selected stored credential. Collision tests must not silently turn a valid configured precedence into a breaking startup error.
- Ownership: `classify-provider-auth-failures`; any new sandbox credential transport belongs to its own approved execution scope, not this research. Confidence: high on documented collision semantics, medium on applicability beyond current native paths.

## 3. No-adopt: iteration/time limits as a spending guarantee
- Source: `run({ maxIterations: 5 })` caps agent iterations (default 1), cached markdown:268-269; `timeouts.copyToWorktreeMs`, `gitSetupMs`, `commitCollectionMs`, `mergeToHostMs` at markdown:289-295. https://github.com/mattpocock/sandcastle#run . These snippets do not establish monetary/token enforcement.
- Counterexample: one iteration can contain retries, multiple completions, or parallel work. A setup/merge timeout bounds that lifecycle step, not provider charges; remote execution can also have infrastructure costs outside model usage.
- Jcode already has non-refundable cross-process council call permits and task inheritance (`crates/jcode-provider-core/src/provider_call_budget.rs:1-3,18-54,70-88`). This is a council call-count mechanism, **not proof of global swarm or currency enforcement**.
- Bounded candidate: carry a resource-unit/scope label through existing budget reconciliation and enforcement work: iteration, elapsed time, call permit, reported tokens, estimated tokens. Distinguish model spend from infrastructure charges rather than promising a universal dollar cap.
- Acceptance: a retried call consumes another permit, concurrent/resumed council seats cannot reset the cap, and unavailable usage remains unknown/estimated rather than zero. Reports cannot label an iteration or time cap as a verified billing limit. Check in-flight request behavior separately; stopping dispatch cannot recall an accepted provider request.
- Ownership: `reconcile-usage-budget-accounting` owns reporting; `enforce-overnight-cancellation-and-limits` owns enforcement. The reconciliation proposal explicitly excludes enforcement and billing conversion (`proposal.md:20-23`). Confidence: high; no claim that Sandcastle lacks undocumented controls.

## 4. No-adopt: best-effort stream logging as authoritative usage accounting
- Source: `logging.onAgentStreamEvent(event)` receives text/tool/raw output, and callback errors are swallowed so logging cannot kill the run (cached markdown:298-308). https://github.com/mattpocock/sandcastle#run . Useful telemetry, not evidence of durable accounting.
- Failure/cost mode: a failed forwarder, disconnected UI, dropped final event, or replay can produce missing/double usage. Raw tool/stdout export can carry credentials or private data. Do not forward complete events merely to reconcile usage.
- Jcode already records terminal usage at transport, not the TUI; captures actual request credential identity instead of the mutable active account; and waits on blocking persistence before forwarding terminal usage (`crates/jcode-provider-openai-runtime/src/openai_usage_recording.rs:1-29,58-94`). The recorder sets its duplicate guard before persistence; this inspection does not establish durable-write failure recovery.
- Bounded candidate: extend existing reconciliation acceptance with **telemetry failure plus ambiguous usage** cases, not another logger: throwing observer, TUI disconnect, replayed terminal usage, account changed midstream, and interrupted stream with no terminal usage event. Keep a bounded typed accounting record separate from raw text export.
- Acceptance: observer failure cannot suppress accounting; one provider response is attributed once to the request's credential; interrupted/no-terminal streams are marked unknown or estimated, never reported as zero actual usage. Verify persistence failure behavior before claiming crash safety. Export nothing beyond approved accounting fields.
- Ownership: `reconcile-usage-budget-accounting`; transport-specific regressions stay in current recorder tests. Confidence: high on present recorder placement, medium on unverified failure recovery.

## Dedupe and disposition
- Existing P06 proposals already own auth taxonomy, usage reconciliation, doctor coverage, transient fallback, and role slots (`docs/plans/PRODUCT_ROADMAP.md:192`). These are acceptance refinements or explicit no-adopt decisions, not five new features.
- Current doctor already distinguishes offline/no-spend, catalog, and full/spending tiers; only full earns strict coverage (`crates/jcode-provider-doctor/src/provider_e2e.rs:1-19`). Do not propose this tier model as net-new based on older proposal text.
- Archive scan found adjacent MCP backoff/management and workflow evidence, not a verified replacement for P06. `openspec/changes/archive/2026-11-02-mcp-failure-backoff/proposal.md` does not establish provider-auth or budget acceptance. Do not equate tool backoff with model-auth recovery.
- No independent reason to adopt Sandcastle's orchestration, dotenv ownership, sandbox vendor, or raw log transport for P06. Existing Jcode auth and accounting boundaries are the cheaper integration points.
