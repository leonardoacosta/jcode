# P07-A: Sandcastle mechanisms for context continuity and privacy

Research only, 2026-11-02. No implementation or new proposal. Four mechanisms below are refinements to existing owners, not four new features.

## 1. Rebase operational session metadata, not transcript prose
**Sandcastle source:** [SessionStore.ts](https://github.com/mattpocock/sandcastle/blob/main/src/SessionStore.ts), `rewriteSessionCwd`, `transferClaudeSession`, `transferCodexSession`, `transferPiSession`.
The pure JSONL transform rewrites matching top-level `cwd` and Codex `session_meta.payload.cwd`; Pi rewrites `type === "session"` header cwd. Nonmatching records, blank lines and malformed lines pass through. Agent-specific entrypoints share the structured rewrite where formats permit it.
**Jcode difference:** Session origin is deliberately guarded: `ensure_initial_session_context_message` preserves a provided working directory instead of replacing it with the daemon's cwd, and `refresh_initial_session_context_message` regenerates the environment message (`crates/jcode-base/src/session.rs:1020-1068`). Project memory files are keyed by path (`crates/jcode-base/src/memory.rs:171-180`). Relocating a session and authorizing a different memory scope are therefore distinct operations.
**Bounded adoption:** Add relocation acceptance cases to existing `workspace-aware-context`, not a foreign-session importer: retain source workspace attribution, refresh live execution context, then resolve allowed memory scope. Do not rewrite arbitrary historical tool output or prose to make it appear native to the destination.
**Acceptance:** Resume/fork A into B where text contains A's path. Live context identifies B, historical prose remains unchanged, A-only memory never enters B without authorized scope. Test missing cwd and daemon cwd mismatch. Future JSONL import must surface malformed-record status rather than assume pass-through records are safe.
**Privacy caveat:** This is path rebasing, **not anonymization**. Transcript bodies can retain usernames, secrets and old paths.
**Confidence:** High for source mechanism, medium for incremental fit. Owner overlap: `workspace-aware-context`; archived `native-instruction-file-loading` already owns instruction precedence, do not duplicate it.

## 2. Treat a session as an explicit artifact family
**Sandcastle source:** [SessionStore.ts](https://github.com/mattpocock/sandcastle/blob/main/src/SessionStore.ts), `claudeSubagentsDirOnHost`, `claudeSubagentsDirInSandbox`, `listClaudeSubagentPathsInSandbox`, `claudeCompanionTransfers`, `readClaudeCompanionsOnHost`, `writeClaudeCompanionsToHost`.
Companion allowlist contains `session-memory/summary.md`, `session-memory/summary-cache.md`, and `file-history/<sessionId>/`. Helpers keep host and sandbox roots explicit. Reads return only existing companion files; subagent enumeration returns an empty list on command failure or missing directories.
**Jcode difference:** Session ancestry and working directory are native metadata (`crates/jcode-base/src/session.rs:129,187`). Memory logs separately persist session IDs and full event details (`crates/jcode-base/src/memory_log.rs:74-98`), and project memory lives outside sessions (`crates/jcode-base/src/memory.rs:171-180`). One session JSON deletion cannot by itself prove complete removal of derived context.
**Bounded adoption:** Extend existing `add-memory-retention-controls` evidence with a documented ownership inventory: session, journals, derived summaries, memory references and event logs. Include descendants only under explicitly stated policy. Do not introduce a second storage service or copy whole provider home directories.
**Acceptance:** Seed a session, descendant, retained memory and event log with distinct sentinels. Preview lists in-scope artifacts and leaves unrelated sessions intact. Execute authorized deletion, then fresh recall/resume must not reconstruct deleted content; shared/global records follow their separate policy. Distinguish missing artifacts from enumeration/I/O failure.
**Caveat:** Sandcastle's allowlist demonstrates bounded transfer, not retention/deletion correctness. Its `catch -> []` is unsuitable as proof that a privacy deletion covered everything.
**Confidence:** High mechanism, medium adoption. Existing `add-memory-retention-controls` already covers logs/backups/caches, so this is an acceptance fixture refinement. Archived `session-store-retention` has unchecked tasks and says archived June 2 despite its Nov 2 archive path; archive location alone does not prove delivery.

## 3. Fail closed on absent source context, but do not copy global lookup semantics
**Sandcastle source:** [SessionStore.ts](https://github.com/mattpocock/sandcastle/blob/main/src/SessionStore.ts), `HostSessionLookup`, `findCodexSessionOnHost`, `findPiSessionOnHost`, `requireHostSessionPath`.
Lookup returns both `path` and `searchedRoot`; `requireHostSessionPath` throws `session ${id} not found in ${found.searchedRoot}` instead of inventing an empty session. Codex recursively scans its session root by filename. Pi tries the cwd-derived directory, then searches other project directories for the ID.
**Jcode difference:** Jcode has explicit project-keyed memory storage and a project field on `MemoryManager` (`crates/jcode-base/src/memory.rs:171-189`). A successful global filename lookup is not evidence that retrieved context belongs to the active workspace.
**Bounded adoption:** In `workspace-aware-context`, require restored session identity plus permitted workspace scope before reusing its derived context. Expose bounded missing-context reasons. **No-adopt:** Pi's other-project fallback as a memory-scope authorization mechanism, and Claude's lossy cwd directory encoding as a new Jcode workspace identity scheme (`encodeProjectPath`, same source).
**Acceptance:** Missing requested source yields an attributable unavailable result, never an unrelated session. Two workspaces with the same relative names and path aliases do not share private recall accidentally. A session ID present only under another workspace remains excluded unless an authorized migration policy applies. Test unreadable source separately from absent source.
**Caveat:** The source catches directory-read errors as not-found, so Jcode should retain an internal error category; user-facing searched roots may themselves expose private host paths.
**Confidence:** High source, medium fit. Existing owner: `workspace-aware-context`; attributable item-level recall remains `add-attributable-memory-recall`.

## 4. Use typed, role-specific handoff context instead of replaying whole transcripts
**Sandcastle source:** [.sandcastle/run.ts](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), `PlanSchema`, planner `promptFile`, `sandbox.run`, `MAX_ITERATIONS`, `MAX_PARALLEL`.
The planner emits `<plan>` JSON parsed through `PlanSchema` into `{number,title,branch}` issues. Execution and review use distinct prompt files plus a small `GH_ISSUE_NUMBER` input, in one sandbox per issue. The script does not interpolate the planner's entire stdout as the implementation/review prompt.
**Jcode difference:** Relevance context is already limited to 1,000 chars per message and six messages (`crates/jcode-base/src/memory_prompt.rs:1-35`), but these are local input limits, not proof of a whole-request budget or cross-role disclosure policy.
**Bounded adoption:** Add a role-handoff scenario to existing `add-prompt-budget-ratchet`: carry only required task identifiers, explicit scope and attributable relevant-memory references. Keep reviewer context sufficient to reproduce findings. No replacement orchestration API.
**Acceptance:** Seed planner history with irrelevant secret sentinels and one necessary constraint. Inspect actual provider requests: only permitted task context and constraint survive, total prompt budget holds, and the worker/reviewer still completes the representative task. Measure actual payloads, not README descriptions or token estimates alone.
**Caveat:** Sandcastle's schema has no array/string length bounds, `JSON.parse` receives the extracted plan wholesale, and prompt files can read further context. This is a useful handoff shape, **not demonstrated prompt-budget or disclosure enforcement**.
**Confidence:** High observed shape, medium benefit. P06 owns orchestration semantics; P07 owns resulting provider payload/budget checks. Avoid a duplicate handoff proposal.
