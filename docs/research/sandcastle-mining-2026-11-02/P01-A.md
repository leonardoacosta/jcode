## 1. Typed planner output before work starts
**Sandcastle mechanism:** `PlanSchema`, `<plan>` extraction, `JSON.parse`, and `PlanSchema.parse` reject absent/malformed plans before issue execution. The schema binds issue `number`, `title`, and `branch`.
**Exact source:** [runner](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), `PlanSchema`, `planJson`, `issues`.
**Jcode difference:** `FollowUpPolicy::decide` already evaluates a native `TodoSnapshot`, not an XML-tagged stdout protocol (`crates/jcode-todo-policy/src/followup.rs:162`). Replacing native task authority with another planner parser would regress the existing contract.
**Bounded adoption:** Reuse native tasks and attach a validated, machine-readable acceptance requirement reference to each selected task. Reject absent/unknown requirement references before launching an acceptance run. Do not import Sandcastle's regex format or branch creation.
**Acceptance checks:** A valid task-to-check binding launches once. Missing/unknown binding is blocked with a reason. Malformed output cannot become a passed check. A task checkbox alone supplies no acceptance evidence.
**Fit/confidence:** Medium. Concrete source mechanism verified by inspection. A requirement-to-check binding is an adaptation, not functionality proven in Sandcastle.

## 2. Setup as a distinct prerequisite
**Sandcastle mechanism:** `createSandbox` receives `hooks.sandbox.onSandboxReady` with `npm install && npm run build`; implementer execution follows sandbox creation. This separates setup configuration from the implementer prompt. The cache does not prove hook failure propagation at runtime.
**Exact source:** [runner](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), `createSandbox`, `onSandboxReady`, `copyToWorktree`.
**Jcode difference:** Native headless setup resolves a working directory, configures memory isolation, and registers directory-scoped MCP tools (`crates/jcode-app-core/src/server/headless.rs:59-99`). `HeadlessMemoryScope::RealProject` and `IsolatedTest` explicitly distinguish real sessions from debug-only isolation (`:17-30`). A headless test is therefore not automatically an isolated acceptance test.
**Bounded adoption:** In the existing acceptance work, record prerequisite outcome, resolved cwd, memory scope, and actual serving identity before executing checks. Use an already-approved test session boundary, not automatic containers, installs, credential mounts, or project-memory changes.
**Acceptance checks:** Setup failure blocks dependent checks. Wrong cwd or real-memory scope in an isolation-required test fails closed. Successful compilation remains a setup result, never the behavior verdict. Interrupted setup leaves an incomplete record rather than pass.
**Fit/confidence:** High for the observed contrast, medium for adoption. Extend existing runtime-evidence work, not a new sandbox feature.

## 3. Preserve independent failure outcomes and enforce a budget
**Sandcastle mechanism:** `MAX_ITERATIONS = 10`, `MAX_PARALLEL = 4`, `acquire`/`release` with `finally`, and `Promise.allSettled` bound execution while retaining rejected issue outcomes. A failed issue need not suppress evidence from another issue.
**Exact source:** [runner](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), `MAX_ITERATIONS`, `MAX_PARALLEL`, `settled`, `outcome.status`.
**Jcode difference:** Continuation already has a gate-attempt budget and stops repeated unchanged ownership gaps (`crates/jcode-todo-policy/src/followup.rs:233-255`). A second loop or scheduler is unnecessary. Sandcastle's runner itself prints rejected outcomes but does not demonstrate a durable acceptance ledger.
**Bounded adoption:** Reuse native continuation limits. Preserve a separate verdict for every attempted acceptance check, including passed, failed, blocked, cancelled, inconclusive, and budget-exhausted. Keep this separate from ordinary task completion and inference success.
**Acceptance checks:** Mixed pass/fail checks retain both outcomes. Cancellation retains finished checks without declaring the remainder passed. Repeated unchanged failures stop at the native budget. Zero checks and exhausted budget cannot produce overall pass. No worker slot remains occupied after an exception.
**Fit/confidence:** High for the source-level mechanisms, medium for acceptance integration. Budget semantics already exist, so this is an evidence-coverage extension.

## 4. Separate implementation and review, but reject the commit-count success proxy
**Sandcastle mechanism:** An implementer runs first; a reviewer runs only when `result.commits.length > 0`. Later `completedIssues` selects fulfilled runs with commits, then a separate merger receives the completed branches.
**Exact source:** [runner](https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/run.ts), `result.commits`, `Reviewer`, `completedIssues`, `Merger`.
**Jcode difference:** Native ownership policy asks whether completed groups have sufficient delivery evidence (`crates/jcode-todo-policy/src/followup.rs:233-249`). The existing acceptance proposal requires runtime-bound evidence, not commit-count inference (`openspec/changes/bind-acceptance-evidence-to-runtime/proposal.md:1-21`).
**Bounded adoption:** Keep independent review as its own evidenced stage against the verified final diff. Record reviewed revision and check-result references. Explicit **no-adopt**: never equate “fulfilled run with commits” with accepted behavior, and never skip review solely because a task produced no commit.
**Acceptance checks:** A commit with a failing check remains failed. A successful no-code acceptance task remains reviewable. Editing the tested/reviewed revision invalidates the prior verdict. Review failure blocks closeout without erasing implementation evidence.
**Fit/confidence:** High for identifying the counterexample and source contrast. No claim that the runner's reviewer actually enforces these checks.

## Dedupe and recommended disposition
- **Extend, do not duplicate:** `bind-acceptance-evidence-to-runtime` already owns source/client/server identity, dirty-state capture, and matched/mismatched/unknown verdicts. Restart-bound invalidation and durable per-check storage are not established by that proposal. Its `tasks.md:3-8` remains unchecked in the inspected checkout. The proposal explicitly excludes storing evidence in sessions/OpenSpec artifacts (`proposal.md:21-23`), so durable per-check storage needs a deliberate scope decision, not silent extension. Add prerequisite and per-check coverage there only after coordinator scope review.
- **Keep separate:** archived `record-continuation-evidence` already owns existing native/log coverage and an offline synthetic baseline. Its `design.md:7-15` explicitly distinguishes source/log facts from serving-runtime proof. It does not establish the new acceptance checks above.
- **Do not recreate:** `admit-judge-feedback-with-bounds`, `restrict-plan-command-execution`, and archived workflow/prompt baselines are already P01 bindings in `docs/plans/PRODUCT_ROADMAP.md:101-115`. No new OpenSpec feature recommended from this report alone.
- Best immediate mining yield: setup outcome + typed per-check verdict + reviewed-revision references inside existing acceptance work. Do not import Sandcastle's scheduler, commit heuristic, merge automation, dependency installs, or credentials behavior.
