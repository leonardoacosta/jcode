## 1. No-adopt: run/bootstrap as an implicit onboarding readiness check
- **Mechanism:** S1 configures `onSandboxReady: [{ command: "npm install && npm run build" }]` on `createSandbox`, then invokes implementation and conditional review agents. This is repository-specific automation, not a harmless credential-presence probe.
- **Failure/security/cost:** dependency installation can execute package scripts, need network access, emit sensitive output and stall. A sandbox factory name does not prove its network, credential or filesystem guarantees. Bringing this into first run changes the user's project before chat.
- **Jcode contrast:** onboarding already renders an explicit escape hatch (`crates/jcode-tui/src/tui/ui_onboarding.rs:23-36`) and distinguishes import progress from failure (`:447-480`). Do not regress these into an unavoidable bootstrap.
- **Bounded disposition:** keep setup discovery inert. If setup later offers an execution check, label its exact effects separately and require an explicit action. Do not add a package-manager/install hook to P09.
- **Acceptance:** offline/no-credential first run remains skippable; rendering setup launches no subprocess and makes no provider request. Import failure remains visible without rerunning installation or silently retrying.
- **Overlap:** `openspec/changes/clarify-first-run-provider-setup/proposal.md:16-22,34-36` already owns provider guidance and chooses presence-only setup. Extend its checks, not a new proposal. Its original problem statement predates current import-state UI, so reverify the remaining gap.
- **Confidence:** high on mechanism and scope mismatch; medium on untested runtime consequences.

## 2. No-adopt: silently refreshing Git while resuming a conversation
- **Mechanism:** S2 describes default reuse of clean branch worktrees with a log, reuse of dirty worktrees with a warning, and default remote fetch plus `--ff-only` when strictly behind. Dirty/diverged/offline cases skip refresh and reuse existing state with a reason. The decision supersedes the unsafe opt-out behavior described in its historical context.
- **Counterexample:** a developer can intentionally resume against the exact old checkout to reproduce a failure. Even a clean fast-forward changes that context. A conversation resume is not a request to synchronize repository contents.
- **Failure/security/cost:** implicit fetch adds network/auth latency; a “resumed” badge can conceal different files from the original conversation. A nonfatal fetch failure is not proof of fresh state. A dirty-worktree warning is not authority to continue code execution, but must not prevent reading an old transcript.
- **Jcode contrast:** `crates/jcode-tui/src/tui/app/inline_interactive.rs:3112-3150` resolves/imports the selected session, reports import failures, short-circuits the current session and queues resume. This inspected TUI boundary is not evidence about every downstream resume effect.
- **Bounded candidate:** add a resume non-mutation contract and, only if existing metadata supports it, distinguish recorded session directory from current workspace context. Do not create worktrees, fetch, reset or repair directories merely by browsing/selecting a session.
- **Acceptance:** opening/filtering/previewing causes no Git mutation or fetch; selecting the current session remains a no-op; offline, dirty and missing-directory fixtures retain transcript access and give a truthful action/error rather than silently changing checkout.
- **Overlap:** `openspec/changes/restore-resume-picker-redesign/proposal.md:11-18` already owns badges, sorting, paging and adaptive layout. Attach boundary tests there; do not duplicate its picker redesign. Any Git-refresh feature belongs outside P09.
- **Confidence:** high on documented counterexample; medium on downstream Jcode non-mutation until exercised.

## 3. No-adopt: hardcoded workflow roles as a model-picker design
- **Mechanism:** S1 chooses `sandcastle.claudeCode("claude-opus-4-8")` for planning, implementation, conditional review and merge. This is one fixed script choice across roles, not discovered account availability, model health or a universal recommendation.
- **Counterexample:** one model name can have several Jcode providers/API methods with different credentials, prices and authority. A CLI adapter choice cannot replace that route identity.
- **Jcode evidence:** `crates/jcode-tui/src/tui/app/inline_interactive.rs:1813-1829` groups by model but retains provider, API method, availability, detail and estimated route cost; `:1733-1739` deliberately avoids local provider defaults for SSH-remote sessions.
- **Failure/security/cost:** copying a “planner = best model” preset can select an unavailable subscription or unexpected paid API route. Local credentials/defaults must not determine remote-server readiness.
- **Bounded disposition:** preserve route-aware selection. Treat Sandcastle role presets as user-authored workflow configuration, never as new default favorites, health indicators or auto-fallback authority.
- **Acceptance:** identical model names on OAuth/API-key/custom routes remain distinguishable; filtering never changes the active provider; selection changes only the explicit chosen route and starts no paid work; remote catalog state does not inherit local credential availability; unknown health stays unknown.
- **Overlap:** `openspec/changes/improve-model-picker-browsing/proposal.md:18-22` already owns browsing, credential-versus-health separation and no automatic health calls. Archived `openspec/changes/archive/2026-11-02-show-resolved-worker-model/proposal.md` owns worker-model visibility, not a fresh picker requirement.
- **Confidence:** high; no evidence that Sandcastle supplies a reusable model-picker mechanism.

## 4. No-adopt: unattended iteration/retry as first-prompt recovery
- **Mechanism:** S1 caps its outer loop at `MAX_ITERATIONS = 10`, queues issue work at `MAX_PARALLEL = 4`, then performs implementation/review and merge calls. `Promise.allSettled` preserves issue-level failure results; missing plan tags throw an error containing `plan.stdout`.
- **Failure/cost:** these caps bound iterations and concurrent issue jobs, not tokens, elapsed time, spend or output volume. Planner output determines issue count without a count limit in the shown `PlanSchema`. A capped loop is not a safe onboarding probe or a bounded billing guarantee.
- **Security:** appending all agent stdout to an error can expose repository/prompt content. Do not transplant this error pattern into compact TUI chrome or telemetry. Console output in a self-authored script is not a terminal-sanitization contract.
- **Jcode contrast:** failed-prompt recovery already forbids automatic resubmission and distinguishes pre-dispatch rejection from uncertain remote outcome: `openspec/changes/archive/2026-10-30-preserve-failed-prompts/proposal.md:9-13`. This is an archived contract, not a newly run test.
- **Bounded disposition:** show the cause and preserve the user's prompt; do not re-run a paid prompt after credential repair/model change without a deliberate send. Reuse existing safe error/copy surfaces, not raw workflow stdout dumps.
- **Acceptance:** duplicate auth/error events create one recoverable failed prompt, no additional provider calls and no overwritten newer draft; repairing login alone does not send; uncertain remote outcome remains explicit. Existing accessibility work owns plain/fallback rendering, not Sandcastle console output.
- **Overlap:** preserve-failed-prompts is delivered scope, not a new feature. `clarify-first-run-provider-setup` owns the actionable login message; `add-terminal-accessibility-fallbacks` owns terminal fallback behavior. Runtime caps/budgets belong to execution/cost phases, not picker UX.
- **Confidence:** high on visible script limits and non-adoption; medium on runtime behavior not executed here.

## Recommendation and validation
- **Net result:** four explicit no-adopt decisions; useful additions are acceptance constraints within existing P09 proposals, not four new OpenSpec changes.
- Prioritize non-mutating resume and non-executing setup/picker checks. Neither Sandcastle documentation nor Jcode proposal status establishes P09 acceptance.
- Validation performed: read P09 roadmap, active setup/resume/model/accessibility proposals, relevant archived prompt/model proposals, cached source/ADR, and current Jcode onboarding/model/resume source spans. No tests/builds/runtime checks were run because this assignment is research only.
