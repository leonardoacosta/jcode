# P02-B: Sandcastle fit and counterexamples

## Verdict
- **Do not add a new P02 proposal from this evidence.** Four explicit no-adopt decisions below. Sandcastle supplies orchestration and repository-layout examples, not verified native/MCP/skill discovery UI.
- P02 requires pre-invocation identity, origin and authority, including remote sessions: `docs/plans/PRODUCT_ROADMAP.md:117-129`.
- Research only. No runtime acceptance, implementation, install, login, network fetch, branch or commit performed.

## 1. No-adopt: copy AFK permission defaults into discovery
- Mechanism: S1 `ClaudeCodeOptions.permissionMode` documents Sandcastle AFK default `--dangerously-skip-permissions`, overridden by explicit `permissionMode`.
- Fit: negative. A tool being discoverable says nothing about permission to invoke it. Sandboxing does not establish approval for credentials, network writes or side effects exposed through MCP.
- Jcode contrast: `openspec/changes/discover-native-and-mcp-capabilities/proposal.md:17-23` specifies read-only listing without invoking tools or starting a lazy server. `docs/plans/PRODUCT_ROADMAP.md:124-129` retains safe invocation and explicit installation decisions.
- Failure/cost: rendering a catalog must not execute an AFK runner, authenticate servers, or consume model tokens. An approval-mode label must not become a grant.
- Acceptance extension, not a new feature: list/filter/refresh with a sentinel lazy-server command and invocation counter. Both remain untouched. Assert unchanged approval settings before/after.
- Confidence: **high** for rejection. Sandcastle permission behavior is README evidence only.

## 2. No-adopt: treat the provider wrapper as a unified capability catalog
- Mechanism: S2 planner calls `sandcastle.run({ sandbox: docker(), agent: sandcastle.claudeCode(...), promptFile: ... })`, then parses `plan.stdout`.
- Fit: provider execution is not discovery. This snippet does not enumerate MCP identity, tool schema, skill provenance, collisions or remote ownership.
- Jcode contrast: `crates/jcode-app-core/src/tool/tests/mcp_collision.rs:3-16,20-39` constructs colliding MCP identities and checks reconciliation. `crates/jcode-base/src/skill.rs:16-25` separately stores skill name, description, allowed tools, content and path.
- Failure/cost: inferring installed tools from provider names creates phantom capabilities. Probing by launching the provider adds latency, inference cost and possible side effects. A remote catalog must describe the serving session, not the local client.
- Acceptance extension: provider configured but unavailable, cached MCP schema stale, two normalized aliases collide, remote peer lacks metadata. Show explicit unavailable/unknown states without probing execution.
- Confidence: **high** for the category distinction, **medium** for broader Sandcastle absence because cached evidence is bounded.

## 3. No-adopt: symlink convention as sufficient provenance
- Mechanism: S4 advertises `.claude/skills` pointing to `.agents/skills`. Useful deduplication convention, not source identity or trust enforcement.
- Jcode contrast: `crates/jcode-base/src/skill.rs:266-285` loads plugins, then Jcode global, then agents global. The same name can select different content under ordered overlays. `skill.rs:417-428` distinguishes installed-plugin sources from the deliberately excluded marketplace catalog.
- Failure/security: a shared physical file can have multiple discovery paths. A symlink target can change after listing. Canonical path alone loses which root won. Scanning a marketplace catalog would advertise uninstalled material.
- Existing owner: `openspec/changes/show-skill-and-mcp-provenance/proposal.md:14-25` already covers discovery root, resolved path, symlink flag, shadowed roots and display-only semantics. Do not create another provenance proposal or reinstall shared skills.
- Acceptance extension: alias paths to one skill, same-name different roots, dangling symlink, retarget between refreshes. Display effective owner plus discovery route. Catalog-only plugin remains absent. Never promote source labels into authorization.
- Confidence: **high** for Jcode overlap, **medium** for Sandcastle mechanism because only linked commit subject was inspected.

## 4. No-adopt for P02: stdout completion watchdog as MCP availability
- Mechanism: S1 `completionTimeoutSeconds` documents a grace window after completion, including spawned MCP servers keeping stdout open. Later output resets the window. README section: `Hanging processes after the completion signal`.
- Fit: useful lifecycle failure example, but unrelated to whether a tool is registered, connected, fresh or permitted. Do not infer server health from a parent agent's completion marker or pipe closure.
- Failure/cost: an inherited stdout pipe can outlive useful work. Conversely, a silent connected server need not be broken. A resettable grace window can add wall-clock cost. No bounded-total-duration claim is established here.
- Jcode overlap: P02 already references `openspec/changes/archive/2026-11-02-mcp-failure-backoff/proposal.md` and `openspec/changes/archive/2026-11-02-tool-timeout-and-patch-recovery/proposal.md` at `docs/plans/PRODUCT_ROADMAP.md:123`. Archive presence is not runtime acceptance.
- Acceptance routing: assess inherited-pipe cleanup under lifecycle/timeout work, not discovery. P02 status must distinguish cached definition from live connection and unknown health without auto-starting the server.
- Confidence: **high** for phase separation, **medium** for documented watchdog implementation.

## Dedupe and blockers
- Existing P02 owners: `add-typed-skill-selector-metadata`, `discover-native-and-mcp-capabilities`, `show-skill-and-mcp-provenance`. Preserve their native precedence, typed rows, control-text sanitation, narrow-width and legacy-peer gates. No duplicate proposal recommended.
- S3 `.sandcastle` is a runner/config directory example, not evidence for a new Jcode discovery root. Existing discovery-root labels and their proposed width cap still need design acceptance at `docs/plans/PRODUCT_ROADMAP.md:128-129`.
- Blocker for stronger adoption claims: no Sandcastle loader/provider implementation or tests inspected, and caches differ in date. No blocker to these bounded no-adopt findings.
- Validation: inspected cached public material, current roadmap, three overlapping proposals, skill fields/load order/plugin-source exclusions, and collision test source. Tests not run because no code changed. Claims distinguish documentation, source inspection and runtime evidence.
