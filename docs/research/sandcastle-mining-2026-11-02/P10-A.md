## 1. Make worktree reuse an explicit, observable starting state
- Source: https://github.com/mattpocock/sandcastle/blob/main/docs/adr/0003-reuse-worktree-by-default.md#decision
- Exact symbols: `WorktreeManager.create`, `run()`, `createSandbox()`, removed option `throwOnDuplicateWorktree`. ADR replaces duplicate rejection with reuse plus clean/dirty diagnostics. Dirty includes staged, unstaged and untracked changes.
- Jcode difference: `crates/jcode-sdk/src/worktrees.rs:110-153` only creates a new branch/worktree, refusing any existing destination at `139-142`. Its tests cover dirty-source isolation, collisions and symlink refusal (`192-232`, `235-261`, `309-317`). This is intentionally safer than silently attaching an agent to an old tree.
- Bounded adoption: retain creation refusal. Add a distinct policy-authorized reuse decision with repository/branch/owner/active-consumer validation and structured starting-state evidence. Warn alone must not authorize dirty-tree reuse. Preserve all files and never reset/clean automatically.
- Acceptance: clean reuse selects the exact expected tree; staged-only, unstaged-only and untracked-only states are distinguished; wrong repository/branch, symlink destination and active conflicting consumer fail closed; denied reuse changes no Git/file state.
- Dedupe: fold into `openspec/changes/configure-task-and-worktree-policy/proposal.md:20-23`, which already owns reuse, freshness, identity and consumer checks. **Refinement, not net-new proposal. Confidence: high design fit, implementation unverified.**

## 2. Distinguish clean from current before reusing a checkout
- Source: same ADR, section “Decision”. Exact Git operations: `git fetch origin <branch>` and `git merge --ff-only`.
- Mechanism: refresh only a clean checkout strictly behind its remote branch; dirty, diverged or fetch-failed trees remain unchanged, with a reason. An isolated sandbox's `.git` is temporary, so its reused worktree does not establish persistence across independent runs. ADR says `createWorktree()` callers must coordinate with live sessions.
- Jcode difference: SDK `create()` starts a new branch at caller `HEAD` (`crates/jcode-sdk/src/worktrees.rs:145-153`), without a reuse/freshness classifier. `git_common_dir_for` groups linked trees by common repository (`crates/jcode-app-core/src/server/util.rs:346-404`), but common identity is not proof of freshness or exclusive use.
- Bounded adoption: add read-only local freshness classification to the existing policy resolver: equal, behind, ahead, diverged, unknown remote, unavailable evidence. Record inspected local/upstream object IDs and timestamps. Keep network fetch and branch mutation separately authorized, never silently fetch merely because a task resumes.
- Acceptance: fixture branches cover each relation; offline/missing remote becomes unknown, not current; dirty/ahead/diverged trees never mutate; stale cached tracking refs are labeled; an authorized refresh rechecks tree/consumer state before mutation and never uses force/reset.
- Dedupe: existing `configure-task-and-worktree-policy` freshness scope plus `reconcile-overnight-runs-after-restart`; report evidence through P10 diagnostics rather than another scheduler. **Confidence: high conceptual fit, medium cost until schema is finalized.**

## 3. Separate executable orchestration from effective configuration evidence
- Sources: https://github.com/mattpocock/sandcastle/blob/main/.sandcastle/main.ts and https://github.com/mattpocock/sandcastle/tree/main/.sandcastle
- Exact source symbols/options: `sandcastle.run`, `docker()`, `MAX_ITERATIONS = 10`, `MAX_PARALLEL = 4`, `promptFile`, `branch`, `baseBranch`. Cached main script supplies provider/model, prompt paths and execution bounds directly at call sites. Listing confirms `.env.example`, `main.ts` and prompt files, not automatic lookup semantics.
- Jcode difference: native config already has global `Config::path()` → `jcode_dir()/config.toml`, environment overrides, strict parsing and read-modify-write protection (`crates/jcode-base/src/config/config_file.rs:18-46`). Do not replace TOML with executable TypeScript or infer a missing upward-search feature from the directory name.
- Bounded adoption: extend the proposed read-only effective-policy view with config path, value source, resolved worktree root, authorization source and resolved prompt/setup path base. Show which scope owns each bound. Display only redacted values, never `.env` contents. Do not execute repository config to inspect it.
- Acceptance: absent/malformed TOML distinguished; environment overrides affect effective output but are not saved; nested/linked-worktree calls resolve the same repository identity; relative paths show their resolution base; project declarations cannot widen user policy or authorize hooks.
- Dedupe: `configure-task-and-worktree-policy/proposal.md:18-23` already owns typed settings, provenance and project restrictions; `repair-provider-environment-config` owns provider/environment repair. **No new configuration system. Confidence: high dedupe, medium source depth.**

## 4. Scope preflight checks to the selected execution platform
- Source: https://github.com/mattpocock/sandcastle#all-options, stale README example `docker({ imageName, containerUid, containerGid, mounts })`. README documents host UID/GID defaults and mismatch preflight; mounts distinguish host `cwd` from sandbox-repository relative bases, with explicit `readonly` and SELinux-label options.
- Jcode difference: current inspected setup is native Rust tooling, not a Docker sandbox. `SetupCheck` and `SelfDevTool::do_setup` check `cargo`, `rustc` and `git` (`crates/jcode-app-core/src/tool/selfdev/setup.rs:5-39,59-91`). No container backend adoption is justified by this research.
- Bounded adoption: reuse `SetupCheck`-style named pass/fail/fix evidence for the selected install/self-dev path, and separate observational probes from repair operations. Record actual platform/tool/build identities. UID/mount checks are conditional ideas only if a separately approved sandbox provider exists later.
- Acceptance: native Linux/macOS/Windows checks do not require Docker; missing dependency yields exact affected capability and manual remedy; observational mode invokes no installer, clone or hook; paths/secrets redact; results identify the serving build rather than only the freshly compiled binary.
- Dedupe: refine `report-install-channel-recovery`, `verify-selfdev-reload-identity` and `record-resource-diagnostics`. Do not create a generic sandbox abstraction or claim supported-platform acceptance from Sandcastle documentation. **Confidence: medium, documented provider behavior only.**
