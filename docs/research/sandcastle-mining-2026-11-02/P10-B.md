# P10 · Lens B · Sandcastle platform/configuration risk assessment

## Scope and evidence
- Research only, 2026-11-02. No implementation, install, login, remote retrieval, branches, worktrees, staging or commits.
- P10 means recoverable installs, declared platform behavior and reproducible diagnostics on the serving build, not sandbox feature parity (`docs/plans/PRODUCT_ROADMAP.md:242-256`).
- Primary external evidence: cached README at https://github.com/mattpocock/sandcastle, `~/.firecrawl/skull-mine-mattpocock-sandcastle.json`. Contract labels it an Oct-28 snapshot, therefore stale. Its local JSON shape changed during this session from `data.markdown` to top-level `markdown`; final findings below were checked against the available top-level text. No commit pin or runtime verification.
- Additional Nov-02 caches: `.sandcastle/` directory listing and worktree ADR. Filenames prove presence only, not setup behavior. Cached `.sandcastle/run.ts` is an orchestration example, not the runtime implementation.
- Existing work owns the relevant mechanisms. These are five explicit no-adopt decisions and bounded acceptance refinements, not new OpenSpec proposals.

## 1. No blanket dependency-directory copying
- Sandcastle: README `createWorktree({ branchStrategy: { type: "branch", branch: "agent/fix-42" }, copyToWorktree: ["node_modules"] })`, https://github.com/mattpocock/sandcastle#readme. This is a documented example, not measured portability evidence.
- Counterexamples: native dependencies built for another OS/architecture, outbound symlinks, executable dependency hooks, and large inode counts. Copy completion does not establish correctness or acceptable setup cost.
- Jcode: `crates/jcode-sdk/src/worktrees.rs:105-151` allocates a sibling root, rejects occupied destinations and invokes Git. The inspected creation path does not copy dependency trees.
- Decision: reject copy-by-default. Any future opt-in transfer needs canonical source/destination, byte/file limits and a platform compatibility warning. Do not execute install commands merely because a copy failed.
- Acceptance: large trees stop at the configured bound; symlink escapes are rejected; cross-platform native dependencies are not reported ready; failure preserves source files and leaves inspectable partial state.
- Dedupe: `configure-task-and-worktree-policy/proposal.md:18-23` already owns roots, permissions, setup declarations and effective policy. Attach only if copying enters its scope, not a separate P10 feature.
- Confidence: high for the documented mechanism and risk. No Sandcastle copy implementation inspected.

## 2. No implicit authority from repository setup hooks
- Sandcastle: README `hooks.host.onWorktreeReady`, `hooks.host.onSandboxReady`, and `hooks.sandbox.onSandboxReady`, https://github.com/mattpocock/sandcastle#readme. Example host command is `cp .env.example .env`; sandbox command is `npm install`.
- Failure mode: two hooks called “setup” can execute against different filesystems and credential boundaries. Repository-provided command text must not itself authorize host execution.
- Jcode: `openspec/changes/configure-task-and-worktree-policy/proposal.md:20-23` separates task permission from repository content and forbids widening host-hook authority. `openspec/changes/add-lifecycle-hooks/proposal.md:9-15` separately owns lifecycle execution.
- Decision: retain explicit execution-location labels, not automatic execution of checked-in TypeScript or shell. Bind any approval to repository identity, command content, execution location and exposed environment names.
- Acceptance: sandbox approval cannot authorize a local hook; changed command/location requires re-evaluation; cancellation prevents dependent phases. Test with harmless commands and synthetic credentials.
- Dedupe: refine lifecycle hooks plus global policy, no second hook runner or new P10 completion credit.
- Confidence: high for documentation and trust-boundary concern; actual Sandcastle approval enforcement unverified.

## 3. No secret-bearing “effective config” dump
- Sandcastle: README `copyToWorktree: [".env"]` and provider-level `docker({ env: { DOCKER_SPECIFIC: "value" } })`, https://github.com/mattpocock/sandcastle#readme. They document explicit transfer/injection surfaces, not protection guarantees.
- Failure mode: copying a conventional filename can expose credentials; logging merged settings can disclose values. Platform/setup diagnostics must distinguish “present” from “safe to display.”
- Jcode: `crates/jcode-base/src/config/config_file.rs:18-46` already provides `Config::path`, environment overrides and `Config::load_strict`; ordinary `Config::load` falls back to defaults on file errors. Machine-local TOML remains the existing source of policy.
- Decision: no new config root or executable config evaluator. Readiness diagnostics should use the strict loader, identify value origin and report environment variable names/presence, never secret values or entire environment files.
- Acceptance: malformed TOML is visibly invalid, not “defaults ready”; environment overrides appear as provenance only; logs and reports contain no sentinel secret; settings updates do not persist transient environment overrides.
- Dedupe: `configure-task-and-worktree-policy/proposal.md:18,23` owns effective-policy provenance. `record-resource-diagnostics` owns redaction and diagnostic limits. This is a boundary check, not a new config feature.
- Confidence: high for Jcode loader behavior; no claim that Sandcastle currently leaks secrets.

## 4. No Docker/cloud prerequisite for ordinary worktree setup
- Sandcastle: README provider table distinguishes bind-mount and isolated providers, accepts `noSandbox()`, and shows `createWorktree` followed by `wt.interactive()` with a documented `noSandbox` default, https://github.com/mattpocock/sandcastle#sandbox-providers.
- Counterexample: adding a container daemon, cloud account, network dependency or paid sandbox to local worktree configuration can make installation less recoverable. A host execution option is not an isolation guarantee.
- Jcode: `crates/jcode-sdk/src/worktrees.rs:25-37,110-151` delegates local creation to Git. `scripts/install.sh:101-146` selects Linux/macOS/Windows install paths; `scripts/install.ps1:3-13` documents the native Windows installer.
- Decision: preserve Git-only local setup. Any sandbox integration must remain separately selected, capability-detected and explicitly authorized. Do not silently fall back from isolation to host execution.
- Acceptance: declared Git-only setup works without Docker or cloud credentials; unavailable selected sandbox gives a clear diagnostic without host fallback; native Windows paths receive real platform checks.
- Dedupe: keep provider execution outside P10 install recovery. Extend `report-install-channel-recovery` only for actual optional-dependency diagnostics, not sandbox adoption.
- Confidence: high for documented API separation; no cross-platform Sandcastle runtime evidence.

## 5. No disposable-worktree cleanup semantics in persistent Jcode work
- Sandcastle: README uses `await using wt = await createWorktree(...)`; the README documents lexical worktree lifecycle. The previously cited `docs/adrs/0001-worktrees-for-branch-isolation.md` was not verified and is excluded from evidence. The actual retrieved ADR is `docs/adr/0003-reuse-worktree-by-default.md`, about reuse/freshness, not proof of crash-safe disposal.
- Failure mode: a normal scoped lifetime is not the same as durable ownership. Automatic deletion after a setup failure could remove a worktree still used by another session or erase the only available recovery evidence.
- Jcode: `crates/jcode-sdk/src/worktrees.rs:105-109` explicitly preserves partial state rather than destructive cleanup. `openspec/changes/configure-task-and-worktree-policy/proposal.md:20-21` requires manual cleanup and active-consumer checks.
- Decision: reject automatic disposal, relocation or prune as setup/distribution behavior. Show bounded recovery diagnostics and exact repository/worktree identity, not a “cleaned up” claim from process exit alone.
- Acceptance: setup failure and daemon reload preserve existing worktrees and unrelated branches; active-consumer conflicts block cleanup; install/launcher/daemon identity checks use the actual serving artifact.
- Dedupe: manual ownership remains in `configure-task-and-worktree-policy`; identity and reload checks remain in `verify-selfdev-reload-identity` and `report-install-channel-recovery`. P10 outcome stays unestablished until its own gates pass.
- Confidence: high for Jcode policy and source behavior; Sandcastle cleanup internals not inspected.
