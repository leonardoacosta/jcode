01ABSORB

/codebase-design

Absorb as shared reference

source ↗
What we found

Defines the precise vocabulary for deep modules: module, interface, depth, seam, adapter, leverage, and locality. It is a reference, not a runnable workflow.

If approved, it lives here
→
  1. Primary: reference material inside /improve-codebase-architecture and /system-architect
  2. Secondary: terminology used by /test-driven-development and /simplify
  3. Governance: authored package after source-level intake, not a second model-invoked skill

Owned surfaces

  • ~/.agents/skills/improve-codebase-architecture/references/
  • ~/.agents/skills/system-architect/references/
  • Descriptions of architecture and TDD skills

Overlap / boundary

Jcode already has architecture decision and review skills. The missing value is a shared vocabulary, not another command.

Required safeguards

  • Keep it non-invokable reference content
  • Retain the deletion test and “one adapter is hypothetical” rule
  • Do not let reference prose improvise an execution loop

Approval consequence

Source-review DEEPENING.md and DESIGN-IT-TWICE.md, then propose one canonical reference atom.

03MERGE

/grilling

Merge frontier mechanics

source ↗
What we found

A dependency-aware interview primitive: map a decision tree, ask the whole current frontier, resolve facts autonomously, and wait on human decisions.

If approved, it lives here
→
  1. Primary: /brainstorming question and approval loop
  2. Native planning: /explore and /feature
  3. Multi-agent facts: Jcode swarm workers under coordinator control

Owned surfaces

  • Brainstorming question scheduler
  • Explore/feature decision maps
  • No standalone /grilling command unless a measured gap remains

Overlap / boundary

The intent strongly overlaps Jcode brainstorming and feature refinement. The frontier algorithm is additive; the wrapper is duplicative.

Required safeguards

  • Facts may dispatch; decisions must wait
  • One question per message remains Jcode’s stronger interaction rule
  • Explicit shared-understanding gate before action
  • No recursive worker spawning outside swarm policy

Approval consequence

Evaluate frontier batching against Jcode’s one-question rule and adopt only the dependency model.

/diagnosing-bugs

Merge into systematic debugging

source ↗
What we found

Six gated phases: reproduce, minimize, rank hypotheses, instrument, fix with regression coverage, and clean up. No theory before a red-capable loop exists.

If approved, it lives here
→
  1. Primary: /systematic-debugging
  2. Runtime proof: /runtime-evidence and /verification-before-completion
  3. Stack-specific diagnosis: /azure-diagnostics, /datadog-cli, /webapp-testing

Owned surfaces

  • Systematic-debugging phase gates
  • Runtime-evidence probe selection
  • Secret-safe instrumentation guidance

Overlap / boundary

Jcode already routes all failures through systematic debugging. The upstream phase gates can deepen that existing skill.

Required safeguards

  • No hypothesis without an observed failing command
  • Instrumentation must follow secrets-handling
  • Stop when environment access blocks reproduction
  • Regression test at the public seam
  • Remove temporary probes before closeout

Approval consequence

Import the tight-loop ladder and phase gates into the existing debugging skill after regression evals.

09ADAPT

/resolving-merge-conflicts

Add conflict-resolution capability

source ↗
What we found

Resolves an in-progress merge or rebase by tracing each side to its intent, preserving compatible behavior, running project checks, and finishing the operation.

If approved, it lives here
→
  1. Primary: new conflict-resolution reference under /merge-to-main
  2. Review discipline: /receiving-code-review for technically questionable resolutions
  3. Execution: git operations remain harness-native and non-interactive

Owned surfaces

  • merge-to-main conflict branch
  • Git-history and issue/PR evidence lookup
  • Verification gates before final commit

Overlap / boundary

Jcode has merge completion but no named intent-first hunk protocol. This should deepen merge-to-main rather than become an unrelated standalone workflow.

Required safeguards

  • Never resolve solely by ours/theirs
  • Read primary intent before editing
  • Do not invent behavior to reconcile sides
  • Abort remains available when merge authorization is withdrawn
  • Verify exact resulting SHA and tests

Approval consequence

Design a bounded merge-to-main conflict branch; do not inherit upstream’s absolute “never abort” rule.

  2. Discovery: /explore for uncertain incoming issues
  3. Disposition: /change-disposition for rejected, deferred, or superseded work
  4. Execution handoff: /feature or one bounded ad-hoc work contract

Owned surfaces

  • Issue-to-feature handoff rules
  • No tracker mutations without authority

Overlap / boundary

Jcode already owns open work, exploration, and disposition as separate skills. The valuable import is the inbound state model and “recommend then wait” rule.

Required safeguards

  • Only triage incoming external reports
  • Verify before readying work
  • Exactly one lifecycle state
  • Never mutate tracker before approval
  • Preserve blocked/deferred states that upstream lacks

Approval consequence

Map upstream states onto Jcode’s richer authority model inside `/open-work`.

  • Reusable audited shell template
  • Temporary generated scripts in repository-approved scratch paths

Overlap / boundary

No existing Jcode skill owns executable human setup walkthroughs end to end. This is the clearest candidate for a genuinely new capability.

  • Hidden secret entry and no transcript echo
  • Static `bash -n` and shellcheck verification
  • Idempotent writes and explicit irreversible gates
  • Delete one-off wizard after completion

Approval consequence

Intake upstream `wizard`, run skill-judge, and pilot one real setup before promotion.

14ADAPT

/code-review

Adapt two-axis review, avoid name

source ↗
What we found

Validates a fixed diff, then reviews repository standards and spec compliance in isolated sub-agents without blending their verdicts.

If approved, it lives here
→
  1. Change interface quality: /interface-review
  2. Review feedback handling: /receiving-code-review
  3. Merge gate: /merge-to-main
  4. Potential internal review agents for Standards and Spec, not a colliding /code-review skill

Owned surfaces

  • Merge-to-main review orchestration
  • Fresh-context reviewer prompts
  • Structured two-axis report artifact

Overlap / boundary

Jcode’s existing review skills cover interface quality and feedback, while merge-to-main owns correctness gates. The two-axis isolation is useful, but the upstream name collides and its recursion bug is unacceptable.

Required safeguards

  • Review committed or explicitly supplied diff
  • Forbid sub-agent re-delegation
  • Standards and Spec verdicts remain separate
  • Every finding cites rule/spec and hunk
  • No convergence loop until “clean”

Approval consequence

Prototype two bounded review agents inside merge-to-main and measure false positives before promotion.
