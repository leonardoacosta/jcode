01 / CLAIM DISCIPLINE

Labels come before conclusions.

Each card uses the evidence label that the repo can support: measured for committed observations, documented for design or implementation notes, and inferred for bounded interpretation. Confidence and limitations are stated inline so the comparison remains useful without pretending to be a benchmark.

  L --> B[Cooperation boundary]

Fallback: Observation windows feed labels; labels feed cooperation boundaries, confidence, limitations, and human-owned handoff decisions.
02 / DAILY SURFACES

Harness cards.

These are working-role comparisons, not rankings. The strongest daily pattern is choosing the narrowest harness that preserves evidence, ownership, and rollback boundaries.

documented · confidence high

Claude Code

Role: external CLI and credential source that Jcode can interoperate with after user approval.

Observed usage: repo docs and code describe Claude Code credential discovery, session search, and live-session takeover safeguards.

Strengths: established coding-agent workflow, native credential surface, and existing session artifacts that can be indexed.

Friction: provider-owned tool execution and credential storage vary by platform, so Jcode treats imports as explicit trust decisions.

Cooperation boundary: use Claude Code artifacts as source material or session handoff context; do not silently read native credentials or mutate live sessions.

documented · confidence medium

Codex

Role: external OpenAI/Codex agent surface and OAuth-adjacent provider lane referenced by Jcode auth and workflow planning.

Observed usage: repository auth notes identify OpenAI/Codex OAuth as a supported integration area, while roadmap notes keep provider-neutral dispatch as an explicit goal.

Strengths: useful as a second implementation or review perspective when the task benefits from provider diversity.

Friction: persisted local evidence is less specific than the Claude Code path in the files inspected for this page.

Cooperation boundary: treat Codex as a peer harness behind documented auth and routing gates, not as an automatically preferred route.

inferred · confidence low

Pi

Role: conversational companion surface in the broader daily ecosystem.

Observed usage: no repo file inspected for this page provides a product-specific Pi integration contract.

Strengths: plausibly useful for lightweight sensemaking, phrasing, and non-destructive ideation when no repository mutation is needed.

Friction: the repository evidence does not support claims about credentials, tools, session import, or automated execution.

Cooperation boundary: keep Pi output advisory unless a future committed adapter or evidence record gives it execution authority.

measured + documented · confidence high

Jcode

Role: repository-native command center for tools, todo state, memory, browser, swarms, docs validation, and provider-aware auth.

Observed usage: the current microsite, validator, OAuth notes, and telemetry page show a field-manual workflow backed by committed JSON, static checks, and explicit decision boundaries.

Strengths: combines local repo authority, evidence maps, static offline pages, and coordination tools in one harness.

Friction: evidence quality still depends on what was committed or deliberately captured; missing pages and stale source matrices remain visible validator failures.

Cooperation boundary: own local orchestration and validation while preserving human approval for risky auth, routing, or handoff decisions.

Evidence claim

documented · confidence medium

Cross-provider agents

Role: coordination pattern for assigning exploration, implementation, review, and verification across model or harness boundaries.

Observed usage: roadmap and telemetry docs describe provider-neutral adapters, model routing evidence, blinded judging, and human approval before production routing changes.

Strengths: reduces single-provider bias and lets one agent check another's work when the evidence loop is explicit.

Friction: coordination can create cost, context drift, and duplicated authority unless task ownership and reporting boundaries are narrow.

Cooperation boundary: coordinate through shared artifacts, claim IDs, and validator output; never let a tournament or peer vote mutate production routing on its own.
