Command Center architecture · decision brief

Durable intent meets live execution.

Jcode should remain the system that decides what work means. Orca should become the system that proves where and how that work is running.

Recommended: layered projection bridge

Generic Orca skills teach mechanics. A focused Jcode skill teaches the policy boundary and the Command Center projection model.

01 · authority

Two planes. One coherent view.

Neither system duplicates the other. Command Center composes both through typed Jcode commands and normalized Orca observations.

Durable plane

Jcode owns meaning and policy

The long-lived record survives workers, terminals, restarts, and UI sessions.

  • Initiatives, milestones, blockers, checkpoints
  • Scheduling intent, retries, outcomes, recovery
  • Permissions, approvals, idempotency, rollback
  • Cross-run evidence and normalized history

Execution plane

Orca owns runtime truth

The live graph says which project, worktree, task, and worker actually exist.

  • Canonical repository and worktree identity
  • Runs, tasks, dependencies, dispatch attempts
  • Workers, terminals, gates, messages
  • Handoffs, retention, release, runtime health

02 · lifecycle

What Command Center actually orchestrates

The UI asks Jcode for an outcome. Jcode chooses an approved Orca pattern, records correlation, then projects evidence back into the same initiative.

Resolve executable identity

Map the initiative to Orca’s canonical repository or project ID. Never substitute the Orca runtime ID.

Select ownership mode

Choose a full handoff for true ownership transfer, or a supervised Run/Task/Dispatch when Jcode must monitor a DAG.

Launch with provenance

Create or reuse the correct worktree and terminal, preserving model, setup, dependency, and mutation ownership rules.

Observe structured lifecycle

Project messages, questions, heartbeats, worker completion, escalations, gates, and terminal health as ordered evidence.

Settle durable outcome

Update Jcode’s initiative and schedule record only from verified Orca receipts. Retain or release runtime resources intentionally.

04 · skill architecture

Three skills, three clear jobs

orca-cli · runtime mechanics

Version-matched worktrees, terminals, comments, browser control, automation, and full handoffs. No Jcode-specific policy.

orchestration · supervised coordination

Runs, tasks, dispatches, messaging, ask/reply, decision gates, worker retention, release, and recovery. Remove obsolete llmtrim guidance.

jcode-command-center-orchestration · policy bridge

Pattern selection, authority matrix, identifier mapping, lifecycle projection, safe mutation capability table, schedule interactions, error states, and acceptance evidence.

05 · alternatives

Why not the simpler options?

Patch only the generic Orca skills

Fast initially, but Jcode policy would leak into version-matched generic guidance. Command Center behavior would be scattered and harder to test.

Make Command Center an Orca-native control surface

It exposes deeper runtime mutation quickly, but conflicts with the approved authority model for initiatives, schedules, permissions, idempotency, and rollback.
