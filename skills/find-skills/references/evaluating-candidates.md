
# Evaluating a Candidate Skill Before Recommending It

## Anti-Patterns (Never Do This)

| Never | Why it bites | Instead |
|-------|---------------|---------|
| Trust a skill's own README/description for freshness or correctness | Author-written claims describe intent at publish time, not current behavior — a skill can say "actively maintained" with an 8-month-stale last commit, or claim compatibility with an API surface that has since changed shape | Check the source repo's last-commit date and open-issue list directly before recommending; marketing copy isn't evidence |
| Install a second skill that solves a problem an existing skill already owns | Two skills with overlapping trigger keywords race for auto-activation — the harness has no tiebreak logic, so which one fires depends on load order, not intent, and neither author knows the other exists to stay in sync | Corpus-search first (references/search-precedence.md); if a near-match exists, extend it or accept its gap instead of installing a competitor |
| Recommend by star count alone | Stars measure popularity at a point in time, not fitness for THIS repo's stack — a 5k-star skill for a paradigm this fleet doesn't use still auto-triggers on keyword overlap and injects wrong-paradigm guidance, which is worse than a 50-star skill that matches exactly | Weight stack match over popularity; a skill that never fires correctly here is dead weight regardless of stars |
| Install without `-a claude-code` | Omitting the flag sprawls `.agents/`/`.crush/`/`.goose/` dirs into the repo — silent multi-tool pollution that reads as unrelated untracked files days later | Always pass `-a claude-code` (`rules/TOOLING.md`) |
| Assume "not in `skill-index.json`" means "doesn't exist" | The index is generated by `build-skill-index.js` and can lag a same-session skill creation | Fall back to `grep -rl` or check `skills/` directly by name before concluding nothing exists |

## Decision Tree: Should I Install/Recommend This Candidate?

Walk these branches in order — stop at the first one that resolves:

1. **Does an equivalent already exist in this repo's corpus?**
   - Yes, exact domain match -> load the existing skill (`Skill({ skill: "<name>" })`). Do not
     install a competitor, even if the candidate looks newer or more polished.
   - Yes, but it's a stale/narrower duplicate (see "Two apparent matches" below) -> flag the
     drift, recommend the routing-table-designated owner, do not add a third option.
   - No equivalent -> continue to 2.
2. **Is the candidate auto-triggered or explicit-only?**
   - Auto-triggered (full natural-language `description` meant to fuzzy-match requests) -> check
     step 3 for keyword collisions before recommending, since it will compete for ambient
     activation.
   - Explicit-only (every invocation is a deliberate `Skill()` call, never ambient) -> keyword
     collision risk is moot; skip to step 4.
3. **Does its trigger language collide with an existing skill's `description`?**
   - Overlapping keywords, same domain -> this is drift, not a green light. Surface it as a
     finding (see "Two apparent matches" below) rather than installing on top of it.
   - No collision -> continue to 4.
4. **What does the staleness/maintenance signal say?**
   - Recent commits, active issue triage, `source:` provenance (if vendored) recently synced ->
     safe to recommend.
   - README claims "actively maintained" but commit history says otherwise -> trust the commit
     history, not the prose (see "README claims currency" edge case below). Recommend with a
     caveat, or hold off if the gap is severe (>6 months, unresolved breaking issues).
   - Can't determine (private repo, no visible history) -> say so explicitly; don't silently
     upgrade "unknown" to "fine."

If all four branches clear, recommend the install/load and cite which corpus lookup path (or
external search) produced the match.

## Fallback / Edge Cases

- **Two candidates solve the same problem differently.** E.g. one wraps a CLI tool, another
  reimplements the logic in-process — both surface on the same keyword search. Prefer the one
  that matches this repo's existing tooling shape (reuse > new, per `rules/CORE.md` Reader Gate)
  over the one that's simply more feature-complete; a feature-rich skill that requires a new
  dependency loses to a thinner one that composes with what's already installed. If truly
  equivalent, prefer the one already cited from `commands/`/`agents/` in this repo — an existing
  citation is evidence it already works in practice here.
- **A skill's README claims currency but has no recent commits.** Don't take the README's word
  for it. Check the source repo's actual commit history and open-issue list directly (same rule
  as the anti-patterns table above). A skill last touched 8+ months ago with open bug reports
  matching your use case is a real risk signal even if its description says "actively
  maintained" — recommend it with that caveat surfaced, or look for an alternative if the gap
  touches the exact functionality being requested.

## Judging a Candidate Skill Before Recommending It

A corpus hit isn't automatically a good match. Non-obvious signals that separate a real match
from a false positive:

- **Auto-triggered vs explicit-only.** Some skills carry a full natural-language `description`
  meant to fuzzy-match a request (`t3-code-patterns`); others are deliberately trimmed to a
  `<=200`-char name + one-line trigger because every real invocation path is an explicit
  `Skill({ skill: "..." })` call from a command or agent frontmatter, never ambient matching
  (`rules/TOOLING.md` § skill-descriptions-budget). A short description isn't evidence a skill is
  thin or unmaintained — check whether it's cited from `commands/`/`agents/` before concluding that.
- **Metadata-only skills are load-bearing, not incomplete.** A skill like `bun`/`docker`/`drizzle`
  can be almost all frontmatter (`category`/`level`/`engineer`/`gate`/`bundles`) with minimal
  prose — that's a stack-composition registration `scripts/lib/compose-stack.sh` consumes, not a
  stub waiting to be filled in. Don't recommend "fleshing it out" without checking whether prose
  depth was ever the point.
- **Two apparent matches for the same domain is itself the finding.** If a search surfaces two
  skills with overlapping trigger language, that's drift worth flagging before recommending
  either — one is likely the intended owner and the other a stale duplicate or narrower
  specialization. Check `rules/PATTERNS.md`'s routing table for the human-decided disambiguation.
- **`source:` frontmatter pins provenance, not currency.** `source: ~/.agents/skills@<date>`
  records when a vendored external skill was last synced — an old date means the local copy may
  have drifted from upstream, not that the skill's behavior is stale. Re-vendor (`npx skills add`
  again) rather than hand-patching if upstream has since fixed something this copy still gets wrong.
