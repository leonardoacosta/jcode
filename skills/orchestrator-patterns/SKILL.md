# Orchestrator Patterns

Reusable multi-agent orchestration library for Claude Code commands. Encodes patterns from 15+
production commands (audit-all, apply-waves, audit-waves, 13 audit-* domain commands).

## Quick Start

Source the helpers in any command that needs multi-agent orchestration:

```bash
source ~/.claude/skills/orchestrator-patterns/scripts/orchestrator-helpers.sh

STATE_FILE=$(orch_state_path "my-command")
CURRENT_SHA=$(git rev-parse --short HEAD)
```

### Initialize or Resume

```bash
if orch_check_resume "$STATE_FILE"; then
  echo "Resuming from previous run."
else
  orch_state_init "$STATE_FILE" "$CURRENT_SHA" \
    "phase_0_preflight" "phase_1_agents" "phase_2_synthesis"
fi
```

### Run a Phase with Skip Logic

```bash
if [[ "$(orch_state_phase_status "$STATE_FILE" "phase_0_preflight")" == "completed" ]]; then
  # Restore cached outputs
  CACHED_VALUE=$(jq -r '.phases[0].agent_outputs.key' "$STATE_FILE")
else
  # Execute phase work...
  RESULT="computed value"
  orch_state_complete "$STATE_FILE" "phase_0_preflight" \
    "{\"key\":\"$RESULT\"}"
fi
```

### Dispatch Parallel Agents

```bash
# Record start time BEFORE dispatch
for node in agent_A agent_B agent_C; do
  orch_state_start_node "$STATE_FILE" "phase_1_agents" "$node"
done

# Dispatch all agents in a single message (subagents run in the background
# by default since CC v2.1.198 — no run_in_background flag needed).
# (This happens in the Claude Code orchestrator, not in bash)

# After each agent completes (Read its output file — TaskOutput is deprecated):
orch_state_update_node "$STATE_FILE" "phase_1_agents" "agent_A" "completed" "$REPORT"
# or on failure:
orch_state_update_node "$STATE_FILE" "phase_1_agents" "agent_B" "failed" "timeout"
```

### Log Telemetry and Notify

```bash
PHASE_END=$(date +%s%3N)
orch_telemetry_log "my-command" "phase_1_agents" 3 $((PHASE_END - PHASE_START)) "$SPEC_NAME" "$PIPELINE_ID"
orch_tts_notify "Phase 1 complete. 3 agents finished."
```

### Print Timing Report

```bash
orch_timing_report "$STATE_FILE"
```

### Clean Up After Success

```bash
orch_state_complete "$STATE_FILE" "phase_2_synthesis" '{"report": true}'
rm -f "$STATE_FILE"
orch_tts_notify "Pipeline complete."
```

## State File Convention

All orchestrator state and telemetry files use a canonical naming convention:

| File Type | Pattern | Example |
|-----------|---------|---------|
| State | `{command}-state.json` | `apply-state.json` |
| Telemetry | `telemetry.jsonl` (unified sink) | `telemetry.jsonl` |
| Pipeline | `.pipeline.json` (per spec) | `openspec/changes/$SPEC/.pipeline.json` |
| Cache | `{command}-cache.json` | `stats-cache.json` |

**Canonical directory:** `$HOME/.claude/scripts/state/`

**Unified telemetry:** All commands log to a single `telemetry.jsonl` via `orch_telemetry_log`.
Pipeline correlation is achieved via `pipeline_id` (generated by `orch_pipeline_id` in `/feature`,
propagated via `.pipeline.json` in the spec directory).

**Helper functions:** Use `orch_state_path` to derive canonical state paths:

```bash
SF=$(orch_state_path "my-command")       # → $HOME/.claude/scripts/state/my-command-state.json
```

The helper auto-creates the parent directory. Always use it instead of hardcoding paths.

## Intermediate Artifacts

**The rule.** When an orchestrator dispatches N parallel agents that each produce structured
output, do NOT collect that output through chat (return values into prompt context). Each
agent writes JSON to disk; the orchestrator merges via a deterministic script that reads from
disk without reloading the JSON into its own context window.

**Why.** Returning N JSON blobs through agent messages bloats the orchestrator's context
linearly with fan-out. Once N grows past ~5 the orchestrator's working context is mostly
agent output rather than judgment. Disk + a merge script makes the merge step deterministic,
inspectable post-run, and cheap. Pattern adopted from Lum1104/Understand-Anything (38k stars,
see `recon://legacy/lum1104-understand-anything-49b27f0e6379/legacy-lum1104-understand-anything-49b27f0e6379d45f` § Steal #2); their CLAUDE.md states it as
discipline: *"Agents write intermediate results on disk (not returned to context). Intermediate
files cleaned up after graph assembly."*

**Canonical layout.** `<project-root>/.cc-state/<command-name>/<run-id>/<agent-id>.json`,
where `<project-root>` is resolved through `wt_main_root_of` (worktree-safe). The
`.cc-state/` directory is gitignored at the project root.

**Canonical helper.** `scripts/bin/cc-state` with subcommands `init`, `write`, `list`.

**Worked example — fan-out + merge:**

```bash
# 1. Orchestrator provisions a run dir once
RUN_DIR=$(scripts/bin/cc-state init --command audit-waves --run-id "$(date +%s)")

# 2. Dispatch N agents in parallel; each agent writes its own JSON to disk
for journey in journeys/*.json; do
  # ... Agent dispatch with prompt that ends with:
  #     "When done, write your findings JSON to
  #      <RUN_DIR>/<journey-slug>.json via:
  #      jq -c . findings.json | scripts/bin/cc-state write \
  #        --run-dir $RUN_DIR --agent <journey-slug>"
done

# 3. Orchestrator inventories results without loading their contents
scripts/bin/cc-state list --run-dir "$RUN_DIR"   # → [{agent_id, path, size_bytes}, ...]

# 4. Merge deterministically (NOT via LLM) — jq over the per-agent cc-state files
jq -s '.' "$RUN_DIR"/*.json > consolidated-report.json
```

The orchestrator never reads individual `<agent-id>.json` files into chat. The merge step is
a deterministic `jq`/script step, not an LLM call.

**When to use.** Any fan-out command with N>3 parallel agents producing structured findings:
`/audit:waves`, `/audit:journeys`, `/audit:code`, `/p2p` bot resolvers, and `/apply:all` wave
dispatch (which consumes the pattern via `neighbor_specs.json`, see § Function Reference). For the
full wave-crew roster (orchestrator / phase engineer / post-wave reviewer roles), the mailbox
contract per artifact, and how this maps onto native CC agent teams once they graduate from
research preview, see [`docs/apply/team-conventions.md`](../../docs/apply/team-conventions.md).

**When NOT to use.** Single agent runs, or fan-outs where each agent commits its own output to
git directly (e.g., `/apply` per-spec engineers — they commit code, not findings JSON).

## Parallel-Agent Git Hygiene

**The rule:** When an orchestrator dispatches N>1 agents that each commit independently against the
same working tree, every agent MUST stage with targeted `git add <specific-paths>`. Never
`git stash`, never `git add .`, never `git add -A`.

**Why it matters.** Parallel agents share one working tree. Stash is a global stack, not an
agent-scoped sandbox — two agents stashing simultaneously produces interleaved entries that
neither agent can confidently `pop`. `git add .` and `git add -A` are equally hostile: each agent
sweeps in every other agent's in-flight files, producing commits that mix unrelated work, fail
review, and corrupt the per-agent diff that downstream review tooling expects. The failure mode
is silent: stash collisions surface as "where did my changes go?" hours later, after a `pop`
restored the wrong agent's edits or dropped a hunk into a conflict that gets resolved away.
Production hit this exact pattern: an e2e-engineer used `git stash` to isolate its commit while
ui-engineer and api-engineer had uncommitted work; no data lost that round, but the next collision
will eat work.

**Worked example — good:**

```bash
# api-engineer dispatch instructions
git add packages/api/src/router/badges.ts \
        packages/api/src/services/badge-issuance.ts \
        openspec/changes/add-badge-tier/tasks.md
git commit -m "feat(api): add badge tier issuance procedure"
git push
```

Each agent names the exact paths it owns. Other agents' in-flight edits stay untouched. The
commit's diff matches the agent's scope exactly.

**Worked example — bad:**

```bash
# e2e-engineer dispatch (WRONG — do not instruct agents to do this)
git stash push -m "e2e isolation"     # collides with ui-engineer's concurrent stash
# ... do work, run tests ...
git stash pop                          # may restore ui-engineer's stash, not its own
git add .                              # sweeps in api-engineer's half-written router
git commit -m "test(e2e): badge flow"
```

Three failure surfaces in five lines: stash collision, wrong-stash pop, and cross-agent file
contamination on `git add .`.

**When the rule applies.** Any orchestrator that dispatches two or more agents (Task tool —
background by default since v2.1.198 — or sequential agents in a single phase) where each agent commits its
own work back to the shared branch. This is the dominant pattern in `/apply:all`, `/audit:waves`,
and any wave-based execution.

**When it doesn't apply.** Solo agent runs (one Task at a time, no concurrent siblings) and
sequential pipelines where agent N waits for agent N-1's commit before starting. In those cases
`git add .` is still discouraged for diff-hygiene reasons but won't cause cross-agent corruption.

### Worktree-Redirect for Persistent State

`/apply` no longer runs inside a worktree (the per-session worktree model was retired 2026-07-17
by `retire-session-worktrees`), so this redirect is now **drain-window-only**: a command that
writes persistent artifacts (recon files, audit reports, screenshots, knowledge graphs) while
running inside a leftover `<repo>/.worktrees/<session-id>/` dir minted before the cutover would
have its writes silently vanish on `wt reap`. Route the output-root resolution through
`wt_main_root_of` from
`scripts/lib/worktree-helpers.sh` — it returns the main checkout root when inside a worktree,
the resolved input path otherwise, and degrades gracefully outside any git checkout.

```bash
source ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude}/scripts/lib/worktree-helpers.sh
OUT_DIR="$(wt_main_root_of "$PWD")/docs/recon"   # survives worktree teardown
```

Opt out per-invocation with `CC_NO_WORKTREE_REDIRECT=1` when you genuinely want a per-worktree
artifact (rare — most callers want the redirect).

## Batch Fix Validation and Fan-Out Gating

> Adapted from millionco/react-doctor's fix-application playbook
> (`recon://legacy/millionco-react-doctor-55de785f44f9/legacy-millionco-react-doctor-55de785f44f9ea2b` Card F).

**Risk-tiered serial-vs-batch.** Not every fix in a batch deserves the same validation cost.
Route by risk: fixes that can silently break something (errors, correctness-bearing changes) run
**serial**, each gated by its own typecheck/test before the next starts, and revert-on-fail so one
bad fix never blocks the rest. Low-risk fixes (formatting, comment-only, mechanical renames with
no behavior change) run **batched** — apply all, gate once at the end.

**Batch failure -> revert-all -> re-apply-serially salvage.** When a batched group's single
end-of-batch gate fails, do not discard the whole batch and do not try to bisect it manually:
revert the entire batch, then re-apply the same fixes one at a time with a per-fix gate. This
isolates the offending fix and salvages every other fix in the batch that passes on its own —
cheaper than either "keep the broken batch" or "throw away every fix because one was bad."

**File-disjoint fan-out: hoist the gate to the parent.** When dispatching N concurrent subagents
each fixing a different, non-overlapping set of files, do NOT have each subagent run its own
project-wide gate (typecheck/test) mid-flight — a project-wide check inside a concurrent fan-out
sees siblings' in-progress edits and can revert a perfectly valid fix because a sibling's file was
mid-edit at that instant. Subagents skip the gate; the **parent** runs exactly one gate after the
whole fan-out completes, then applies the batch-fail salvage loop above if it fails. This mirrors
the merge-slot serialization principle elsewhere in cc (one holder, checked at the right layer)
applied to validation instead of git writes.

## Function Reference

### State Management

| Function | Purpose |
|---|---|
| `orch_state_init <file> <sha> <phases...>` | Create state file with phase list |
| `orch_state_complete <file> <phase> [outputs]` | Mark phase completed, cache outputs |
| `orch_state_phase_status <file> <phase>` | Get phase status string |
| `orch_state_start_node <file> <phase> <node>` | Record node start time before dispatch |
| `orch_state_update_node <file> <phase> <node> <status> [data]` | Update node with auto-computed duration |
| `orch_state_node_status <file> <phase> <node>` | Get node status within a phase |

### Resume Detection

| Function | Purpose |
|---|---|
| `orch_check_resume <file> [--fresh]` | Check if state is resumable (returns 0) or needs fresh start (returns 1) |

### Timing & Display

| Function | Purpose |
|---|---|
| `orch_fmt_duration <ms>` | Format milliseconds to human-readable string |
| `orch_timing_report <file>` | Print phase + node timing table from state file |

### Telemetry

| Function | Purpose |
|---|---|
| `orch_telemetry_log <command> <phase> <agent_count> <wall_ms> <spec_name> <pipeline_id>` | Append JSONL entry to unified sink (`telemetry.jsonl`) with auto-rotation at 100 entries. `spec_name` and `pipeline_id` may be `"null"` for commands without spec context. |
| `orch_pipeline_id` | Generate UUIDv4 for pipeline correlation across commands |

### Notifications

| Function | Purpose |
|---|---|
| `orch_tts_notify <message>` | Fire-and-forget TTS notification via say_notify |

### Intermediate Artifacts (cc-state)

Standalone CLI at `scripts/bin/cc-state` — invoke directly, not via shell function.

| Invocation | Purpose |
|---|---|
| `cc-state init --command <name> [--run-id <id>]` | Create `<wt_main_root>/.cc-state/<name>/<run-id>/` and emit the absolute path on stdout. `run-id` defaults to epoch-ms + 4-byte hex. Worktree-safe via `wt_main_root_of`. |
| `cc-state write --run-dir <path> --agent <id>` | Read JSON from stdin; atomic write to `<run-dir>/<agent>.json`. Validates agent id (`^[a-zA-Z0-9_-]+$`) and JSON. Exit 2 on bad JSON. |
| `cc-state list --run-dir <path>` | Emit `[{agent_id, path, size_bytes}]` JSON array on stdout (sorted by `agent_id`). Does NOT print file contents. |
| `cc-state --self-test` | Built-in roundtrip test (init → write → list → assert). Exits 0 on PASS, 1 on FAIL. |

`/apply:all`'s wave dispatch is the canonical consumer: `wave-plan-build build --state-run-dir <path>` writes a `neighbor_specs.json` artifact that `engineer-preamble.sh --spec-name <name> --run-dir <path>` reads to render a "Cross-spec coordination" section in each engineer's prompt.

## Minimal Multi-Agent Command Skeleton

Complete example of a 3-phase command using all patterns:

```bash
#!/usr/bin/env bash
# /my-multi-agent-command — runs N agents across M phases
source ~/.claude/skills/orchestrator-patterns/scripts/orchestrator-helpers.sh

SF=$(orch_state_path "my-command")
SHA=$(git rev-parse --short HEAD)
PIPELINE_ID=$(orch_pipeline_id)
SPEC_NAME="${1:-null}"  # pass spec name if applicable, "null" otherwise

# --- Resume detection ---
FRESH_FLAG=""
[[ "${ARGUMENTS:-}" == *"--fresh"* ]] && FRESH_FLAG="--fresh"
if ! orch_check_resume "$SF" $FRESH_FLAG; then
  orch_state_init "$SF" "$SHA" "preflight" "agents" "synthesis"
fi

# --- Phase 0: Preflight ---
if [[ "$(orch_state_phase_status "$SF" "preflight")" != "completed" ]]; then
  P0_START=$(date +%s%3N)
  # ... run preflight checks ...
  PREFLIGHT_RESULT="ok"
  orch_state_complete "$SF" "preflight" "{\"result\":\"$PREFLIGHT_RESULT\"}"
  orch_telemetry_log "my-command" "preflight" 0 $(( $(date +%s%3N) - P0_START )) "$SPEC_NAME" "$PIPELINE_ID"
else
  PREFLIGHT_RESULT=$(jq -r '.phases[0].agent_outputs.result' "$SF")
fi

# --- Phase 1: Parallel agents ---
if [[ "$(orch_state_phase_status "$SF" "agents")" != "completed" ]]; then
  P1_START=$(date +%s%3N)
  NODES_TO_SPAWN=()
  for node in worker_A worker_B worker_C; do
    status=$(orch_state_node_status "$SF" "agents" "$node")
    if [[ "$status" != "completed" ]]; then
      NODES_TO_SPAWN+=("$node")
    fi
  done

  # Record start times BEFORE dispatch
  for node in "${NODES_TO_SPAWN[@]}"; do
    orch_state_start_node "$SF" "agents" "$node"
  done

  # >>> DISPATCH: spawn Task calls here (background by default since v2.1.198) <<<

  # After each agent completes (Read its output file — TaskOutput is deprecated):
  # orch_state_update_node "$SF" "agents" "worker_A" "completed" "$REPORT"

  orch_telemetry_log "my-command" "agents" ${#NODES_TO_SPAWN[@]} $(( $(date +%s%3N) - P1_START )) "$SPEC_NAME" "$PIPELINE_ID"
fi

# --- Phase 2: Synthesis ---
if [[ "$(orch_state_phase_status "$SF" "synthesis")" != "completed" ]]; then
  P2_START=$(date +%s%3N)
  # ... synthesize reports from all agents ...
  orch_state_complete "$SF" "synthesis" '{"report_generated": true}'
  orch_telemetry_log "my-command" "synthesis" 0 $(( $(date +%s%3N) - P2_START )) "$SPEC_NAME" "$PIPELINE_ID"
fi

# --- Timing report + cleanup ---
orch_timing_report "$SF"
rm -f "$SF"
orch_tts_notify "Pipeline complete."
```

Adapt this skeleton by:
1. Replacing phase names with your command's phases
2. Replacing node names with your agent identifiers
3. Adding domain-specific preflight and synthesis logic
4. Choosing agent types per `references/agent-dispatch.md`
