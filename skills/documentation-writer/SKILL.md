# Documentation Writer

MANDATORY: before authoring, auditing, or scaffolding a repo's `docs/` tree, read
`references/operational-docs-canon.md` in full. That file — not this one — carries the
house-specific expertise: directory roles, the frontmatter contract, correction-banner
convention, and the probe-block verifiability contract a staleness sweep checks against. The
generic Diátaxis framework (tutorial / how-to / reference / explanation, https://diataxis.fr/)
underlies all of it but needs no restatement here.

## Choosing the Genre First

Before wording, decide what KIND of document this is. Genre is expensive to change later: a
decision buried in a living page gets edited away the next time the page is updated, and a
reference page written as a dated record goes stale and nobody dares touch it.

The split that governs everything is **receipts vs state** (canon § Receipts vs State) — not
topic, but maintenance rule:

| | Receipts | State |
| --- | --- | --- |
| Rule | Append-only, dated, **never edited after the fact** | Living, corrected in place, pruned |
| Trustworthy because | It was not edited | It is kept current |
| Genres | `docs/adr/` records, `docs/notes/` entries, correction banners | `reference/` pages, `guides/`, MOCs |
| Fails by | Going stale while staying true about its moment | Losing the reasoning that produced it |

| You are writing | Genre | Lands in |
| --- | --- | --- |
| Why we chose X over Y, and what we rejected | ADR | `docs/adr/NNNN-title.md` |
| How the subsystem works right now | reference page | `docs/reference/` |
| What an investigation turned up, on a date | note | `docs/notes/` |
| Steps to accomplish a task | guide/runbook | `docs/guides/` |
| Where to find things — "read this when X" | MOC | that directory's `index.md` |

A useful test when torn between an ADR and a living page: **ask whether the reasoning stays
valuable after the decision is reversed.** If yes, it is a receipt — an ADR, superseded by a
later ADR rather than edited. If the page only needs to describe today's state, it is state, and
the reasoning belongs in an ADR the page links to. Recording both in one file is what makes wikis
rot: the half that must not change and the half that must are fighting each other.

### PKM: which ideas to keep

"Use a PKM format" is a reasonable instinct, but the tools lost and the ideas won (canon
§ Navigation Layer; `recon://legacy/docs-canon-v2-recon-2026-07-22-913141c0b6f3/legacy-docs-canon-v2-recon-2026-07-22-913141c0b6f38ffc` § 4.4). Keep: **atomic pages**
(one concern per file, stable path — agents retrieve per-file), **MOCs** (curated annotated
indexes, not `ls` output — the value is the routing note), and **maturity markers** (the
`status:` frontmatter field). Reject **wikilinks** — GitHub does not render them and they break
for any agent reader outside the tool that invented them; use standard relative links.

PKM organizes the corpus; ADR is one genre inside it. They are not alternatives, and a tree can
run both — `~/dev/brown/ws/docs` does, with a `Home.md` portal, `start-here/` role routers, and
`status:` frontmatter throughout.

Full detail — including the journal layer and its promotion paths (journal → bead / memory /
ADR / note) — is in `references/operational-docs-canon.md`. Read it before authoring.

## Repo `docs/` Tree Conventions

Distilled from the canon below — quick reference only; the canon file is the source of truth.

| Directory | Role | Lifecycle |
| --- | --- | --- |
| `reference/` | How-it-IS state per subsystem; some pages are machine-written artifacts | Long-lived, corrected in place |
| `notes/` | Dated investigation journal, one note per investigation | Short-lived; superseded notes move to `notes/archive/` |
| `guides/` | Step-by-step runbooks | Long-lived, corrected in place |
| `diagrams/` | Visual explainers (`.mmd` source + rendered `.svg`/image) | Long-lived, paired with its source |

Do not blend roles — a runbook that drifts into investigation narrative, or a reference page
that turns into a journal entry, breaks the reader's ability to trust the directory by its
name alone.

- **Frontmatter**: every page carries `status: current|draft|superseded` + `updated:
  YYYY-MM-DD` — the machine-checkable freshness signal a staleness sweep reads, not git mtime.
- **Corrections**: never silently edit away a claim later found wrong — add a dated
  `> **CORRECTION (YYYY-MM-DD):**` banner directly above it.
- **Machine artifacts**: a script-generated `reference/` page gets a `<!-- GENERATED by
  <script> — do not hand-edit -->` marker on its generated section; edit the generator, not
  the page, and let its `status`/`updated` reflect the last generation run.
- **No vendored build output** (e.g. a git-tracked docs-site `node_modules/`) under `docs/`.
- **Age is not decay**: an old page whose claims still verify against the current repo is
  healthy. Decay is a dangling path/command reference, or a claim the repo now contradicts —
  fix those, don't rewrite for age alone.
- **Verifiability**: phrase countable claims (a count, an exact path, an exact command) so a
  probe block can confirm them for free — a fenced ` ```bash ` block whose first line is
  `# probe: <expected substring>`, placed beside the claim it backs.
