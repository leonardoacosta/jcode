# QA Test Planner

Template generator for manual QA artifacts: test plans, test cases, regression suites,
bug reports, and Figma design-validation checklists.

> **Activation:** explicit only — invoke by name (`/qa-test-planner`, "use the skill
> qa-test-planner"). It does not auto-trigger on generic testing language.

## Scope Note (honest assessment)

The template layer below (test plan structure, bug report severity levels, regression suite
cadence) is vendored generic QA-process knowledge — no fleet-specific judgment was layered onto
the templates themselves. What this skill DOES add is fleet-specific judgment on the seam where
manual QA meets this repo's automated testing system: see **Escalation Judgment** below for the
decision criteria on bead-vs-e2e-test, and how a manual finding's tag choice determines whether it
can even land as automated coverage under `t3-testing-patterns`' CI tag gate. The templates
themselves earn their keep as a **template/checklist generator** for the manual-QA artifacts
`t3-testing-patterns` doesn't produce (a human-readable test plan document, a bug report someone
files in a tracker, a Figma-vs-implementation checklist).

## Escalation Judgment: Bead vs. Automated E2E Test

A manual QA finding is not automatically either "file a bead" or "write a Playwright spec" — the
call is a genuine trade-off, not a coin flip. Decide on three axes together, not any one alone:

| Axis | Push toward **e2e regression test** | Push toward **tracked issue only** |
|---|---|---|
| Severity | Critical/High — breaks a core journey, causes data loss, or is a security gap | Low/Medium — cosmetic, edge-case copy, non-blocking UX friction |
| Reproducibility | Reliably reproduces (2/3+ manual attempts hit it) | Intermittent, or only reproduces under a rare state combination |
| Automation cost | Cheap to fixture — existing `@fixtures/base` helpers, no new mocked service | Expensive to fixture — needs a new webhook race, a third-party mock, or device-specific state |

**All three point the same way -> act on it now.** High severity + reproducible + cheap to
automate means write the e2e spec today, in the same pass as the manual finding — a manual QA
pass only catches the bug once; without a regression test it silently reappears on the next
deploy with nobody manually re-walking that exact path.

**Mixed signals -> bead first, promote on repeat.** A severity-Low or expensive-to-fixture
finding becomes a tracked issue under the owning feature, not an
immediate e2e spec — forcing every manual finding into automation inflates suite runtime and
unbalances Rule 8's shard map (`t3-testing-patterns` § Shard Map: `@slow`/`@visual` already carry
the expensive tests; padding that lane for a one-off cosmetic bug taxes every CI run for
negligible protection). If the same finding resurfaces on a later manual pass, that recurrence
*is* the signal to promote it to automated coverage — the same Promotion-on-Repeat logic
governs memory-vs-rule promotion applies here to manual-finding-vs-test.

**A flaky finding is worse automated than un-automated.** If reproduction is unreliable even
manually, do not force it into a Playwright spec just to "have coverage" — a flaky e2e test erodes
trust in the whole suite (gets skipped, ignored, or quarantined) faster than an honestly-tracked
bead does. Automate only what actually reproduces.

### Tag-Gate Interaction (does manual QA block CI?)

`t3-testing-patterns`' Rule 8 tag-coverage gate is purely mechanical — it checks that every
`test.describe` carries an allowlisted tag (`@smoke`, `@critical`, `@payments`, `@admin`,
`@staff`, `@slow`, `@serial`, `@a11y`, `@visual`, `@regression`, `@api`) and has no awareness of
manual QA passes at all. A manual QA finding never blocks or unblocks that gate directly.

The real connection point is one step downstream: when a finding IS promoted to an automated spec
per the table above, that spec must carry one of the allowlisted tags before the gate will let it
land — an untagged spec fails Rule 8's CI check regardless of how well it was manually verified.
**A test plan generated by this skill should name the target tag at plan time, not leave it for
whoever automates it later** — a finding tied to a payment flow proposes `@payments`, one tied to
a core signup/login path proposes `@critical` + `@smoke`, a cosmetic-but-worth-automating finding
proposes `@regression`. Naming the tag in the plan document is the concrete artifact-level bridge
between a manual test plan and the automated coverage system — without it, tag selection becomes
a guess made after the fact, disconnected from the manual investigation that justified the test.

## When a Manual Test Plan Is the Right Tool (vs. Writing the E2E Test Directly)

Escalation Judgment above answers "what do I do with a finding I already have." This section
answers the earlier question: given a task that needs validating, is a manual QA pass even worth
doing in a fleet that already runs automated e2e coverage — or should the effort go straight into
a Playwright spec instead? Three fleet-specific costs make automation *not* the default answer:

| Cost | Mechanic (`t3-testing-patterns`) | What it means for planning effort |
|---|---|---|
| Shard budget is finite | Shard 1 (`@critical`+`@smoke`) targets <3 min; shards 2-3 carry bulk regression; shard 4 (`@slow`+`@visual`) already runs long | Every automated test is a **permanent** CI-time tax — Rule 8's tag gate means nothing drops out silently once added. Right for something that will regress; wrong for a one-time check |
| Data-isolation setup cost | Rule 9: mutating tests need per-test create+teardown; a novel mutation vector (new webhook race, third-party mock) has real fixture-authoring cost | A finding that needs a new fixture to automate is expensive to validate twice — manually confirm it's real *before* paying that setup cost (same principle as Escalation Judgment's automation-cost axis, applied one step earlier) |
| Visual regression is pixel-diff, not design-intent | Rule 11's baseline diff catches byte-level drift between CI runs, not "does this match the Figma design" | A Figma-vs-implementation comparison is inherently a manual-judgment task — automating it would mean encoding design intent as a pixel tolerance, which Rule 11 explicitly does not attempt |

**Manual test planning wins when:** the target UI is still in flux (locators would churn daily —
a spec authored today is wasted effort by next week), the check is a one-time validation
(migration verification, pre-launch checklist, a Figma-vs-implementation comparison) that won't
recur in that exact shape, or a finding needs cheap human judgment before committing to an
expensive fixture build.

**Skip the manual plan and write the e2e spec directly when:** the flow already has stable
selectors and predictable inputs. Producing a manual test-case document first only delays the
artifact that actually catches future regressions — a test plan for a flow that's already stable
enough to automate is process theater, since nobody re-runs a manual document once the Playwright
spec exists to do it automatically on every PR.

## Writing Steps That Promote Cleanly (Manual -> Automated Bridge)

Escalation Judgment above decides *whether* a finding gets promoted to an e2e spec; this section
is about *how the manual test case is worded* so promotion is a translation, not a rewrite. An
author who doesn't know `t3-testing-patterns`' e2e conventions naturally writes steps that promote
straight into the anti-patterns those rules ban — the fix is phrasing the step in promotable form
the first time, not cleaning it up after automation.

| Write the manual step as... | Promotes directly to (`t3-testing-patterns`) | Vague version reintroduces |
|---|---|---|
| A named action + accessible locator hint: "Click the 'Add to Cart' button (role=button, name='Add to Cart')" | One `test.step('add to cart', ...)` block (Spec Structure convention) wrapping `page.getByRole('button', { name: ... })` | "Click the button" forces the automator to re-discover the locator from scratch |
| An explicit wait condition, not a duration: "Wait until the cart-count badge reads '1'" | Rule 7's condition-based wait (`expect(...).toBeVisible()` / `toHaveText(...)`) | "Wait a few seconds" has no automated equivalent — it gets promoted as `waitForTimeout`, the exact pattern Rule 7 requires a `@wait-exception` justification to keep |
| A flagged mutation: "Creates a new vendor application (mutating)" | Rule 9's per-test create+teardown vector | An unflagged mutating step gets promoted onto the shared-baseline/readonly assumption and races other tests under shard rotation |

Group a multi-action manual case into named phases (e.g. "Phase 1: add to cart", "Phase 2: pay") —
the same separation you'd already use as section headers maps 1:1 onto `test.step` boundaries, and
is what makes a later-failing promoted spec attributable to a phase instead of a flat locator dump.

| Ask for | Get |
|---------|-----|
| "Create a test plan for {feature}" | Strategy, scope, entry/exit criteria, risks |
| "Generate test cases for {flow}" | Step-by-step cases with expected results |

| "Create a bug report for {issue}" | Reproducible steps, environment, evidence |

## Anti-Patterns

| Avoid | Why | Instead |
|-------|-----|---------|
| Vague test steps | Can't reproduce | Specific actions + expected results |
| Missing preconditions | Tests fail unexpectedly | Document all setup requirements |
| No test data | Tester blocked | Provide sample data or generation |
| Generic bug titles | Hard to track | Specific: "[Feature] issue when [action]" |
| Skip edge cases | Miss critical bugs | Include boundary values, nulls |

---

## Verification Checklist

**Test Plan:** scope defined (in/out) - entry/exit criteria specified - risks identified with mitigations - timeline realistic.

**Test Cases:** each step has an expected result - preconditions documented - test data available - priority assigned.

**Bug Reports:** reproducible steps - environment documented - screenshots/evidence attached - severity/priority set.
